# Planning Completeness And Execution Eligibility

Use this contract for Stage 9, workpack creation/refresh, and later authorized execution. It changes validation selection, not product authority or execution permissions.

A complete plan has settled required behavior and contracts, named producers and proof owners, coherent bounded scope and verification, and no material unresolved decision, contradiction, unknown producer, dependency cycle, or unjustified exclusion. It may await a defined output from another complete producer plan. Prepare every requested slice whose planning prerequisites are satisfied, including later execution groups; keep one stable handoff/workpack per slice. The sequence remains execution navigation. Link a complete future handoff from its `Waiting` row; creating it does not advance the current group or mark implementation complete.

## Validation And Review

Planning callers explicitly pass `--validation-mode planning` to delivery readiness, selected handoff sequence checks, the Stage 9 wrapper, and workpack validation. Execution callers explicitly pass `--validation-mode execution`; omitted mode retains strict execution semantics. Unknown modes and unsupported combinations fail. Build-only validation does not accept the CLI option. Execution-record start/check accepts only execution mode; start always reruns strict readiness. A planning PASS cannot create an execution record or authorize source edits.

Reuse `Delivery Slice Realizability Review` and `Workpack Integrity Review`. `Review result: PASS` means the plan's bounded review is complete. All common planning axes still PASS; only Stage 9 `Execution-context readiness` and workpack `Execution eligibility` may be `WAITING` with exact INPUT/INT producer waits or the earlier order group, plus canonical links. `Review blockers: None.` excludes unresolved planning decisions, not declared execution waits. In execution mode those axes must PASS and every required upstream output must be verified. Never replace contradictory observations with a structural PASS.

## Planned Dependencies

For a future output from a separate planned producer, use `Availability: planned upstream output` in the existing INPUT/INT entry. Keep the canonical producer, consumer, consumption stage, logical contract, physical binding and proof owner unchanged. Add:

- `Producer handoff`: a link to the producer's exact `#output-NNN` declaration in its current handoff. That handoff must have a settled READY/PARTIAL planning outcome, and its slice must be an earlier direct `Requires` edge. An already-created stable producer workpack may additionally be linked; do not invent it.
- `Expected output`: exact capability/output name, matching the producer declaration.
- `Expected contract`: exact approved contract/version expectation, matching the declaration. Link approval/contract authority in the surrounding canonical sources; an expected identity is not an actual artifact digest.
- `Consumption point`: the start/phase and public consumption seam that needs it.
- `Availability check`: the actual acquisition/identity/producer-conformance checks and applicable existing-consumer compatibility required before use; schedule final proof through a new selected consumer after its implementation.

In the producer's existing Allowed Delivery Slice section, declare `### OUTPUT-NNN` with `Output`, `Contract`, `Owner` (one code-formatted BUILD_UNIT), `Writable paths`, `Contract authority` (canonical contract or Approved/Inherited selection link), and `Verification`. Its owner must be writable there. Promised output requires a realizable producer plan, not a bare dependency name. Review the producer records and relevant scope/verification; a declaration alone is not proof of feasibility.

Planned INPUT maturity is `not-applicable`; actual artifact identity, source revision, integrity, resolution/access results, upstream receipt and availability evidence are `None.` until observed. Planned INT conformance and consumer challenge remain `Planned`, never Verified/PASS. Do not assert provider availability, successful tests or execution observations. `selected-slice output` still means this workpack's writable owner creates it; `later-lifecycle output` still requires its original LGATE and cannot hide implementation/build/verification prerequisites; `missing` still blocks plan completeness.

A PSEAM covering planned INPUT/INT uses `Producer observation: PLANNED_UPSTREAM_OUTPUT`, `Current result: AWAITING_UPSTREAM`, `Delta owner: None.`, and PLANNED candidate proof with `planned-proof` provenance. Retain all compared dimensions, allowed command effects, current consumer observations where they exist, bounded change-impact dispositions, and final proof routes. Existing protected implemented evolution still requires its focused compatibility probe. Future final proof remains scheduled, not observed.

Project these dependency fields exactly into the workpack's INPUT/INT obligation, rebasing links. A selected read-only producer waiting on that output is `Planned prerequisite`, with verification-only `Planned prerequisite` RCOV coverage; use `Existing prerequisite` only for actual existing dependencies. Neither role grants writable authority. Do not select an upstream unit merely to name a dependency or include unrelated runtime journeys in a bounded delta.

## Feasibility Within The Existing Review

Planning validation requires bounded `### CAP-NNN` entries in the existing Stage 9 realizability review. Review every essential implementation capability and verification tool using focused source/interface inspection and safe probes. Cover source changes, tests, fixtures, assurance adapters, manifests, lockfiles, generators/generated outputs, verification routes and required command effects. A verification procedure must be runnable by permitted work.

Each CAP entry records `Capability`, `Disposition` (`Existing`, `Selected-slice output`, or `Planned upstream output`), `Owner`, `Allowed interface`, `Required changes`, `Evidence`, and `Verification`. List the approved repository-relative writable ceiling in the review's `Writable paths` field using backticked paths; reconcile it with the approved Allowed Delivery Slice boundary, never invent a larger ceiling. For Selected-slice output, enumerate Required changes as backticked paths beneath that ceiling and use one writable Build Unit owner. For Existing/Planned upstream output, Required changes is `None.`; cite actual allowed-interface evidence or the exact defined planned INPUT/INT dependency. An unresolved capability or adapter outside that ceiling blocks completion. These records make assumptions inspectable; validators cannot prove that the reviewer found every essential capability or that a claimed observation is true.

Before later source edits, recheck the applicable assumptions against the actual target. A missing public address-validation/output-script capability with no approved writable implementation or named contracted producer blocks planning. A missing assurance adapter cannot be delivered under a ceiling permitting only coverage-route edits. Passing structural validation never overrides either contradiction.

## Authorized Continuation And Evidence

Creating, updating or migrating plans authorizes planning only. Reports and generated follow-ups end at the requested planning endpoint. The workpack's execution instructions are conditional instructions for a later authorized run, not authorization. Never supply a prompt that says implement merely because execution is next.

One-workpack authorization ends at that workpack. Explicit sequence/cohort authorization permits execution in dependency order using the existing skills and host continuation mechanism. After an eligible producer completes, inspect its actual output and compatibility against the expected contract, then perform bounded downstream design/planning reconciliation, revalidate execution eligibility, capture exact final workpack content/snapshot through the existing start mechanism, and continue to the next authorized slice. Routine reference/receipt updates under unchanged approved behavior, contract, ownership and scope require no renewed approval. No new runner, scheduler or registry is needed.

For a reconciled upstream INPUT/INT, retain its expected dependency fields and bind `Upstream receipt` to actual completed producer evidence. Use verified existing availability only for the input or interaction actually observed. The linked record includes `Output`, `Contract`, `Producer`, `Outcome: COMPLETE`, `Executed snapshot`, and `Executed workpack content`; append output observations to the existing producer summary when appropriate, without rewriting historical execution fields. For an existing consumer, perform the specified availability/compatibility check and bind `Availability evidence` to actual consumer proof with `Outcome: PASS`, exact `Output`, `Contract`, and `Consumer`. Omitted `Availability evidence scope` retains this consumer-fitness requirement; a scoped prerequisite check cannot substitute for it. A producer receipt alone cannot establish consumer fitness. A historical Implemented row or receipt for another contract cannot satisfy a newer requirement. A material incompatibility requires reassessment, not automatic acceptance or a changed expected contract.

### New Consumer Against An Available Producer

An available producer does not imply that a new consumer is implemented. Before B starts, verify A's real output identity/availability, applicable approved representation/contract conformance, and every required compatibility check against existing consumers. Do not require B's own final integration result before implementing B. Retain required consumer-fitness classes and schedule final proof within B's approved writable scope; it must PASS before completion, even when prerequisite validation passes.

For this explicit case, use `verified existing input` on the resolved INPUT and `selected-slice consumer` on the INT. Retain A as the canonical read-only Producer; B is the writable Consumer and explicit Proof owner. This INT means B will implement consumption of the verified producer, not that A or the interaction is a selected producer output. Keep INT `Representation conformance` and `Consumer challenge` as `Planned` with concrete local proof-owner/verification links. The existing PSEAM covering these entries uses `new-output`, `Producer observation: OBSERVED`, `Consumer observation: SELECTED_SLICE_OUTPUT`, `Current result: DELTA_OWNED`, B as `Delta owner`, PLANNED candidate proof and `planned-proof` provenance. Its observation text distinguishes actual A evidence from planned B work. Retain all scope/feasibility checks and applicable existing-consumer/protected-evolution probes. This representation cannot defer an existing implemented consumer's fitness or an unsatisfied lifecycle gate.

Add `Availability evidence scope: prerequisite` to the INPUT/INT. Its linked availability record contains `Scope: prerequisite`, `Outcome: PASS`, matching `Output`, `Contract`, and `Consumer`, `Producer identity` (the observed applicable revision/artifact/service identity), `Producer conformance: PASS` with a linked actual check, and `Existing-consumer compatibility: PASS` with linked existing-consumer evidence. Use `Not applicable` for the latter only with linked bounded evidence showing no applicable existing-consumer obligation; an existing required check cannot be deferred or waived. When citing acquired local bytes, additionally record `Artifact` (one local link) and `Artifact identity` (their exact sha256); the validator checks these bytes. Retain existing INPUT immutable-artifact identity/acquisition requirements. Do not impose a universal per-source hash or mistake a captured API response for proof of live provider availability. This is prerequisite evidence, not completed B fitness. Acquisition checks, producer-local checks and fixtures describe only what they actually establish.

Project the evidence scope exactly into the workpack. Map each prerequisite-scoped INPUT/INT through its existing Coverage to at least one final VE with `Evidence scope: consumer-fitness`, a concrete post-implementation consumer procedure, observed-result requirements and an owned feasible route. Completion SUMMARY records that same VE as PASS with `Evidence scope: consumer-fitness`; Planned, missing or prerequisite/producer/fixture-only proof does not complete B. Validators verify declared structure and artifact bytes, not the truth or adequacy of claimed behavioral results. Never fabricate an observed result to satisfy them.

Stop affected work for material product/protocol behavior, architecture/public contract, new dependency/capability choice, writable-scope expansion, conflicting authorities, or an assumption materially changing the plan. Explain evidence, alternatives, recommendation and consequences; continue independent authorized work where safe. Do not ask again for recorded decisions or disguise a new choice as routine reconciliation.

## Current Plans And History

A known newer unexecuted plan may differ from the last implemented receipt. Preserve the recoverable exact implemented workpack, prior summary, start identity and implementation report; cite that established basis in the existing Readiness Decision. Planning refresh does not advance implementation evidence or fabricate execution identities. Compare the old report with its actual implemented basis, not automatically with the newest unexecuted plan. Unknown historical association still requires the separately authorized legacy-lineage recovery route.

Documentation-only implemented-identity synchronization remains the existing reviewed no-impact operation when actually requested; it is not an automatic consequence of drafting a newer plan. Interrupted attempts retain their prior exact digest and summary; reconcile through the existing rules rather than replacing a stored digest.

Lead current-state reports with requested objective, planning completion, execution eligibility and exact waits, whether application code changed, decisions needed and next authorized action. Distinguish structural success, complete planning, eligible execution and completed implementation/verification. Where an ongoing review exists, put its short current-state summary first and retain detailed history with superseded conclusions identified. Use existing records only.

## Adoption

Existing strict ready documents retain their execution/default meaning. No bulk consumer migration is required. A separately authorized planning refresh adopts CAP review entries, explicit planned dependencies and conditional handoff wording where applicable. Preserve external audience identities, separate proof owners, selected-output ownership, lifecycle-link comparison, dynamic prototype evidence, bounded exclusions, symlink execution and exact execution history.
