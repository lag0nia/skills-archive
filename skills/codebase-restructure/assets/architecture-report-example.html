Summary

Objective

“Check this repository's structure and suggest improvements.” Find where the structure makes ordinary changes costly, and propose a coherent target with a safe migration. Inspect and plan only.

Recommendation

First give the shift eligibility rules a single owner: they are copied in two places, one rule change was already missed in a copy, and the one remaining difference between the copies is undocumented. The move keeps today's behavior. Then move reminder sending out of the confirmation request, which fails confirmations whenever the email provider is slow. Leave the admin screens where they are.

Overall target

Two independent changes move Rota toward one organization in which each rule and each side effect has a single owner. Eligibility rules move to one module that both the API and the importer call; where the two paths deliberately differ, that module states the difference. Reminder delivery becomes the notification module's responsibility, fed by an outbox written in the same transaction as the confirmation. Everything else keeps its current shape.

Candidate 1

Give shift eligibility one owner

  • Recommendation: Strong
  • Priority: first
  • Effort: moderate
  • State: Proposed

Why Strong: two copies of the same rules, a recorded defect caused by a missed copy, and a contained remedy, with two callers to migrate, that keeps current behavior.

Problem

Three rules decide whether a volunteer may take a shift: minimum age, required training and no overlapping shifts. The API applies all three inside assignVolunteer(); the roster importer re-implements training and overlap in validateRow() and does not check age. Every rule change so far has needed two edits, and one was missed for two months. Nothing in the code says whether the missing age check in imports is deliberate.

Evidence and paths
  • server/shifts/assign.ts: assignVolunteer() checks age, training and overlap inline before saving.
  • tools/import-roster.ts: validateRow() checks training and overlap with its own code; no age check. The last commit to change its checks is “Allow youth pilot imports” (2024).
  • History: 6 of the 8 commits that changed either rule set changed both files. “Require first-aid training for night shifts” changed only the API; “Fix importer night-shift training” followed two months later.
  • Tests: test/assign.test.ts covers the API rules; the importer's rules have no tests.

Interface sketch (proposal, not an approved contract)

// server/shifts/eligibility.ts
const MINIMUM_AGE = { confirmation: 16, import: null };  // import: no minimum, as today (see Q1)

checkEligibility(volunteer, shift, existingShifts, path)   // path: "confirmation" | "import"
  → { eligible: true }
  | { eligible: false, reasons: ["under-minimum-age" | "missing-training" | "overlaps", …] }

// tools/import-roster.ts, per row
const result = checkEligibility(row.volunteer, row.shift, await shiftsFor(row.volunteer), "import");
if (!result.eligible) report(row, result.reasons);   // every failing rule, not only the first

Callers must know the four inputs, including which path they are, that the function performs no database access (callers load existing shifts), and that it returns every failing rule, which the importer needs in order to report all problems in a row at once. It hides the rule definitions, their order and which rule differs by path. The one difference sits in a single line, and tests pin it for both paths. Because the function is pure, it is tested directly, and both callers' tests exercise it through their own entry points.

Proposed change

Move all three rules to server/shifts/eligibility.ts; both callers use checkEligibility() and say which path they are. Today's age difference becomes an explicit, tested rule for the import path. The importer maps the shared reason codes to its current messages.

Gains

One place to change a rule; importer rules gain tests; a missed copy can no longer happen; the age difference is stated and tested instead of an unexplained gap.

Costs

Characterization tests for the importer first, and a small mapping to keep its messages. One rule still differs by path, stated next to the others, until Q1 settles whether it is still wanted.

Compatibility

No behavior change in either path: confirmations reject volunteers under 16 and imports accept them, as today. Only an answer of (a) or (b) to Q1 would change who is eligible, in its own later step.

Uncertainty

Whether imports should still accept volunteers under 16: “Allow youth pilot imports” (2024) suggests the difference was deliberate, but the roadmap no longer mentions youth programmes. See Q1.

Migration outline

  1. Characterize both paths, including imports accepting volunteers under 16 (ready)
  2. Move all three rules into the eligibility module, keeping the import age rule explicit and tested; both callers use it (after step 1 is completed and verified)
  3. Change the import age rule (waiting on Q1, needed only if (a) or (b); after step 2)

Candidate 2

Send reminders after the confirmation is saved, not during it

  • Recommendation: Worth exploring
  • Priority: second
  • Effort: moderate
  • State: Proposed
  • Conflicts with a recorded decision

Why Worth exploring: the cost is real and recorded, but the recommended option changes an implemented decision and needs an answer about duplicate reminders (Q2) before its retry step.

Problem

Confirming a shift saves the assignment and then waits for the email provider before responding. When the provider is slow, the request times out after the assignment is saved: the volunteer sees an error for a shift they now hold, and many confirm again. A bulk import confirms each row the same way, so one provider outage stops the whole import.

Evidence and paths
  • server/routes/shifts.ts: confirmShift() awaits sendReminder() from server/notify/email.ts before responding; the provider client uses a 30 second timeout.
  • docs/ops-notes.md records two manual clean-ups of duplicate assignments after provider incidents.
  • tools/import-roster.ts calls the same confirmation path for each row.

Conflicts with a recorded decision: “Reminders are sent inline” in maintenance/decisions/repository.md, status Implemented. Its reason was that a volunteer must never believe they are confirmed without receiving a reminder.

What changed since: confirmed shifts now appear in the volunteer's own shift list, so the email is no longer the only confirmation; and provider timeouts now produce duplicate assignments.

Why reconsidering is justified: the decision's own reconsider-when condition, “confirmation becomes visible elsewhere”, is met.

Proposed change

Confirmation writes an outbox row with the assignment; a worker loop in server/notify/ sends due reminders and marks them sent. See the alternatives.

Gains

Confirmations and imports no longer fail because of the provider; reminders survive restarts and are retried.

Costs

An outbox table migration, a worker loop in the process lifecycle, and a table to monitor.

Compatibility

The API response keeps its shape but no longer implies that the email was sent. Updates the recorded decision once approved.

Uncertainty

A crash between sending and marking can send a reminder twice (Q2). How often the process restarts is unknown: deployment configuration was not accessible.

Migration outline

  1. Characterize confirmation and reminder behavior (ready)
  2. Add the outbox table and write rows in the confirmation transaction (after step 1, and after Candidate 1 step 2 to keep edits to the route apart)
  3. Add the worker with retries and skip cancelled assignments (after step 2; waiting on Q2)
  4. Remove inline sending and update the decision record (after step 3)

Candidate 3

Split the admin screens into a separate package

  • Recommendation: Speculative
  • Priority: not now

Why Speculative: separate packages are a frequent suggestion for a codebase of this shape, but nothing here needs one.

web/admin/ and web/volunteer/ share one build and many components, and changed together in 11 of the last 14 releases. The roadmap mentions no separate admin release or access boundary. Splitting would add a second build and a shared component package for no current benefit.

Reconsider when: admin screens need their own release cadence, hosting or access boundary.

Questions

Q1 Should imports keep accepting volunteers under 16?

Decision: confirmations reject volunteers under 16; imports accept them. Step 2 of Candidate 1 keeps that difference, explicit and tested, in the one eligibility module, whatever the answer. This question is only whether the difference is still wanted.

Why it matters: it decides whether step 3 of Candidate 1 exists, and whether partner organisations can keep importing youth rosters.

  • (a) Apply the minimum age to imports too. One age rule for both paths. Imports containing volunteers under 16 would report those rows as ineligible; existing assignments are not touched. A behavior change for partners who import youth rosters.
  • (b) Allow supervised volunteers under 16 in both paths. Keeps the youth pilot and extends it to confirmations, which changes the API's behavior. Needs a way to record supervision, which becomes a follow-up decision.
  • (c) Keep today's behavior. The import exception stays as a named, tested rule in the eligibility module, with its reason recorded. No behavior change; the cost is one path-specific rule to maintain and explain, and the question of whether the pilot still needs it stays open.

Recommendation (provisional): (c) for now. The 2024 commit suggests the difference was deliberate, and changing it could reject partner imports without warning. The repository cannot show whether partners still import youth rosters; if the pilot has ended, (a) removes the exception with a one-line change in the eligibility module and its tests.

Affects: Candidate 1, step 3 only. Steps 1 and 2 do not depend on the answer: step 1 is ready, and step 2 waits for step 1 to be completed and verified. Neither has been executed.

If you choose (b), a follow-up question about how supervision is recorded will follow.

Q2 After a crash, is a duplicate reminder acceptable to ensure none is lost?

Decision: with an outbox, a crash between sending and marking forces a choice between sending twice and possibly not sending at all.

Why it matters: it sets the worker's retry behavior, which the tests of step 3 will pin.

  • (a) At least once. Mark after sending. A reminder is never lost; after a crash, one may arrive twice.
  • (b) At most once. Mark before sending. Never duplicated; a crash at the wrong moment loses the reminder.
  • (c) Deduplicate at the provider. Send an idempotency key so the provider drops repeats. Best of both, if the provider supports it; its documentation is not in the repository, so this is unverified.

Recommendation: (a), adding (c) if the provider supports keys. A duplicate reminder is a minor annoyance; a missing one causes no-shows, which is the cost the current decision was written to avoid.

Affects: Candidate 2, step 3.
