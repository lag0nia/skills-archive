## Execution Eligibility

**Validation mode.** Execution callers pass `--validation-mode execution`; omitted mode keeps strict execution semantics, and unknown modes or unsupported combinations fail. In execution mode every review axis must PASS and every required upstream output must be verified. Execution-record start and check accept only execution mode, and start always reruns strict readiness. A planning PASS never creates an execution record or authorizes source edits.

**Authorization.** Creating, updating, or migrating plans authorizes planning only, and reports end at the requested planning endpoint. A workpack's execution instructions apply only to a later authorized run; never supply a prompt that says implement merely because execution is next. One-workpack authorization ends at that workpack. Explicit sequence or cohort authorization permits execution in dependency order: after an eligible producer completes, inspect its actual output against the expected contract, reconcile bounded downstream design and planning, revalidate execution eligibility, capture the exact final workpack content and snapshot through the existing start mechanism, and continue to the next authorized slice. Routine reference and receipt updates under unchanged approved behavior, contract, ownership, and scope need no renewed approval; add no runner, scheduler, or registry.

**Before source edits.** Recheck the applicable feasibility assumptions against the actual target. A missing public capability with no approved writable implementation or named contracted producer blocks, and a delta outside the writable ceiling cannot be delivered. Structural validation never overrides either contradiction.

**Upstream outputs.** For a reconciled upstream INPUT/INT, keep its expected dependency fields and bind `Upstream receipt` to actual completed producer evidence carrying `Output`, `Contract`, `Producer`, `Outcome: COMPLETE`, `Executed snapshot`, and `Executed workpack content`; append output observations to the producer summary without rewriting historical execution fields. Use verified existing availability only for what was actually observed. For an existing consumer, run the specified check and bind `Availability evidence` to actual consumer proof with `Outcome: PASS` and exact `Output`, `Contract`, and `Consumer`; omitted `Availability evidence scope` keeps this consumer-fitness requirement, which a scoped prerequisite check cannot replace. A producer receipt alone never establishes consumer fitness, and a historical Implemented row or another contract's receipt never satisfies a newer requirement. A material incompatibility requires reassessment, not acceptance or a changed expected contract.

**New consumer.** An available producer does not mean a new consumer B exists. Before B starts, verify the producer's real output identity, applicable conformance, and every required existing-consumer compatibility check; B's own final integration result is not a precondition. B is complete only when its mapped final VE records PASS with `Evidence scope: consumer-fitness`; Planned, missing, or prerequisite, producer, or fixture-only proof does not complete it. Validators check declared structure and artifact bytes, not the truth of claimed results; never fabricate an observed result.

**Stop.** Stop affected work for material product or protocol behavior, architecture or public contract, a new dependency or capability choice, writable-scope expansion, conflicting authorities, or an assumption that materially changes the plan. Explain evidence, alternatives, recommendation, and consequences; continue independent authorized work where safe. Do not ask again for recorded decisions or disguise a new choice as routine reconciliation.

**History.** A known newer unexecuted plan may differ from the last implemented receipt. Preserve the recoverable exact implemented workpack, prior summary, start identity, and implementation report, and cite that basis in the Readiness Decision. Compare the old report with its actual implemented basis, never automatically with the newest plan; planning refresh does not advance implementation evidence or fabricate execution identities. Unknown historical association requires the separately authorized legacy-lineage recovery route. Documentation-only implemented-identity synchronization runs only when actually requested, never as a consequence of drafting a newer plan. Interrupted attempts keep their prior exact digest and summary; reconcile rather than replace a stored digest.
