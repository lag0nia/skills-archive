## Purpose And Boundary

Use this mode to turn approved technical truth into independently buildable artifacts, concrete code locations, internal module boundaries, target-outcome assembly ownership, runtime-profile claims, environments, commands, reusable selections, verification capabilities, and Delivery Planning readiness. It is not a second Software Design pass, an implementation plan, a workpack, or code execution.

For a human-facing application or operator surface, also read [ui-ux-design.md](ui-ux-design.md). UI/UX Design owns presentation and interaction requirements while this reference owns construction and delivery routing. Existing system contracts continue to own behavior.

The `system-model/` owns system behavior, authority, externally visible interfaces, state transitions, lifecycle rules, invariants, and correctness claims. Build Design owns how those responsibilities are realized in code while preserving those contracts. If a proposed local interface changes a system contract, stop and repair Software Design first.

Do not add an implementation runner, execution/review workflow, or universal test-framework policy in this mode. The assurance traceability contract may route canonical VOs to repository-owned evidence and a later normalized report; it does not execute that evidence or prescribe test counts, frameworks, or CI vendors. A repository-specific agent-guidance contract and derived guidance artifact are allowed when required by the repository contract coverage audit; they must not become canonical architecture or replace the Build Design. A downstream workpack may implement one build unit, part of one, or a coordinated slice across several build units.

## Build Design Concepts

- **System Domain:** coherent logical concern grouping System Responsibilities. It is not a build phase, repository, deployment unit, or automatically a DDD bounded context.
- **System Responsibility:** stable logical behavior, authority, state, or artifact boundary with one owning Domain. It is not necessarily one package, service, or workpack.
- **Build unit:** independently buildable and testable application, service, worker, library, contract package, CLI, or tooling artifact with a stable `BU-xxx` identifier.
- **Repository Build Design:** source-control repository/workspace construction contract for one or more build units with a stable `REPO-xxx` identifier. It is not a build unit, module, or delivery slice.
- **Module:** internal folder, package, namespace, or code boundary inside one build unit. Use actual module names and paths; do not create global module IDs.
- **Delivery slice:** the capability selected for downstream planning. It may require one or several build units and is not another maintained architecture hierarchy.

Map System Responsibilities and Build Units many-to-many. One responsibility may span client, server, worker, or shared-library units. One Build Unit may realize parts of several responsibilities. Never infer one Build Unit per responsibility, one repository per Build Unit, or one workpack per Build Unit. Technical Constraints are the stable IDs for decided technical dos and don'ts; Build Design maps them to the units and repositories that must preserve them.

## Stage 8 And Stage 9 Operations

### Stage 8: Build Design

Use Build Design when the user wants package boundaries, repository topology, independently buildable artifacts, or module architecture and the approved System Responsibilities are stable enough to map. A new package normally reaches this point after Stage 7. It may proceed while implementation-detail tickets remain unresolved, and later ticket discovery updates the mapping without retroactively invalidating it.

For every in-scope human-facing surface, consume the Stage 7 UI/UX specification, selected candidate entrypoint, and reviewed journey coverage under [UI/UX Design](ui-ux-design.md). Use its selective routes into the portable module. Do not shift required discovery to Stage 8 or automatically render pending later prototype changes; an explicit prototype-change or synchronization request authorizes affected work. Relevant reconciliation is required before claiming selected-scope UI readiness.

If no human-facing surface is in scope, do not create `ui-ux/`. A library, background service, pipeline, or infrastructure-only Build Design remains complete without an HTML prototype. An explicitly design-only scope may stop before Stage 8 or Stage 9 and must not imply UI implementation readiness.

When a historical Stage 7 completion response or temporary coverage ledger is unavailable, do not block Build Design for that reason alone. Perform a bounded current-state check: confirm that every approved System Responsibility has a canonical owner, inspect current direct handoffs and authority boundaries for a concrete contradiction or missing responsibility, run the ticket lead report and structural validators, and verify that the current ticket corpus is inspectable. If no concrete gap prevents truthful artifact mapping, proceed and report that historical snapshot completeness was not re-proven. If a concrete gap does prevent mapping, pause only that boundary and route it to the owning ticket or Software Design repair.

Create only build units justified by an actual build/test artifact boundary. Record unresolved mapped tickets as blockers; do not hide them and do not claim planning readiness. Once any build-unit record exists, give every active ticket a `build_units` inline array. Use an empty array only with a concrete `build_unit_disposition` such as external/no-code responsibility, outside the mapped Build Design scope, or no artifact impact.

For every approved target outcome and required runtime profile, run an assembly-ownership challenge. Identify the intended actor or consumer, real entrypoint, startup/shutdown or invocation path, required dependencies and configuration, bootstrap/seed/migration behavior, identity and resource discovery, persistence/resume/reset semantics, external prerequisites or approved substitutes, minimum observable result, and acceptance proof owner. Assign each concern to existing Build Units when it belongs to their coherent artifacts. Create a dedicated composition, developer-runtime, or demo Build Unit only when the concern forms an independently buildable and testable artifact; do not create one universally. A repository-root script, environment declaration, or test harness with no Build Unit owner is not coverage for a claimed runnable outcome.

Create one `REPO-xxx` Repository Build Design for every first-party source repository containing one or more mapped Build Units. It records repository versus workspace shape, member units, canonical package/code paths, repository-owned `RC-xxx` rules, and the complete applicable subset of member-unit `CONS-xxx` records. Its human `## Repository Overview` includes a `### Material Workspace Tree` showing the repository root, workspace/package roots, Build Unit homes, material shared source/test/fixture/generated/evidence/tool roots, and root configuration—but never expands a member's internal code. Link the owning Build Unit record for that detail. Its `## Agent-First Canonical Reference` owns the exact construction sections. A vendor, external system, or no-code disposition is not a first-party repository and must use an explicit Build Unit `repository_disposition` instead. Run a repository discovery pass after the repository grouping is known: derive rules fixed by Build Units, CONS records, and SEL/VA records; derive required conventional files and configuration from the selected stack; leave only genuinely reversible private implementation choices local; and create a normal `TICKET-NNNN` ticket for each material unanswered repository choice. When a ticket is specifically about repository construction, set its optional `repositories` array to the affected `REPO-xxx` records; do not use its `build_units` array as a repository proxy. Do not ask for a machine-specific worktree path or whether obvious files such as package manifests, workspace configuration, lockfiles, or required CI configuration should exist. Do not wait for every mapped ticket to resolve before mapping a repository, but do not declare it handoff-ready while repository discovery is incomplete.

### Repository Contract Coverage

Read [maintainability-and-agent-guidance-baseline.md](maintainability-and-agent-guidance-baseline.md) for every first-party repository. The baseline supplies portable defaults; it does not silently decide repository-specific architecture.

For each `REPO-xxx`, build a coverage receipt with exactly these lanes:

- `repository-module-conventions`: package/workspace shape, package and module naming, canonical source/test/fixture placement, public entrypoints and barrels, import/dependency direction, configuration, CI, release, and the version-control/generated-file boundary.
- `code-construction-public-api`: paradigm and module style, data/value representation, mutation and lifecycle, placement of logic/types/interfaces/schemas/errors/fixtures, public function/method/factory shape, capability and sync/async boundaries, error taxonomy and transport, redaction/cause/retry behavior, side-effect placement, and test idioms.
- `maintainability-agent-guidance`: simplicity defaults, abstraction and duplication admission, naming/refactor hygiene, minimal outputs, wrapper avoidance, rationale comments for non-obvious complexity, agent change boundaries, stop/escalate conditions, and verification expectations.

Classify each lane as `inherited`, `resolved`, `adapted`, or `not-applicable`. An `adapted` or `not-applicable` result requires a concrete reason, affected scope, and verification or revisit condition. If a material lane is missing, create one normal `TICKET-NNNN` ticket per cohesive lane, set `repository_contract_area` to the lane value, map `repositories` to the affected Repository Build Design, and map `build_units` to every affected unit. Ask the user the ticket questions in the ordinary batch format, give a recommendation and consequences, and do not leave the builder to choose the lane privately. Existing authoritative repository rules may satisfy a lane; do not create duplicate tickets merely because the repository uses different names or a different but explicit convention.

For the `maintainability-agent-guidance` ticket, load `references/maintainability-and-agent-guidance-baseline.md` and expand it into an answerable decision packet. Never ask the user to approve only `maintainability-agent-guidance-baseline`. Show the recommended REPO-specific rule, at least one viable alternative or explicit reason the baseline is inherited unchanged, and the consequence for each numbered area: (1) simplicity and abstraction, (2) duplication and refactoring, (3) naming and rationale comments, (4) agent change boundaries, (5) stop/escalate conditions, and (6) verification and final-diff review. Explain which parts are inherited and which are open to adaptation. The user may accept or revise each numbered rule; record the expanded rules in the ticket resolution and the derived guidance artifact.

When all applicable lanes are resolved, update the Repository Build Design and create a derived guidance artifact at `build/repositories/repo-xxx-<slug>/agent-guidance.md`. Keep the full actionable rules in this guidance artifact rather than duplicating them in the repository README. It must identify the baseline version, source tickets, canonical design links, hard rules, defaults with exception guidance, rationale-comment policy, stop/escalate conditions, and verification expectations. When the actual repository exists, materialize its root `AGENTS.md` from this artifact; do not make the generated file a competing source of architecture.

### Version-Control And Generated-File Policy

Every first-party Repository Build Design with `discovery_status: complete` must contain `## Version-Control And Generated-File Policy` with exactly these concrete fields:

- `**Must track:**` canonical source, configuration, lockfiles, workflows, fixtures, evidence, manifests, or other reviewable repository inputs that cannot be silently ignored;
- `**Must ignore:**` dependency directories, build products, coverage, caches, test reports, logs, editor/OS metadata, local environment files, or other disposable or machine-local outputs implied by the selected stack;
- `**Generated-output disposition:**` which outputs are transient, reproducibly generated and untracked, or intentionally versioned and reviewed;
- `**Secret/template rule:**` which secret-bearing files remain local and which redacted example or schema files may be committed; and
- `**Verification:**` the repository-local command or procedure that proves representative must-ignore and must-track paths follow the policy.

Derive ordinary stack-specific ignore entries and safe template exceptions automatically. Do not ask the user about `.DS_Store`, dependency caches, compiler metadata, or similarly reversible conventional entries. Create or reopen a `repository-module-conventions` ticket only when a material alternative changes review, release, security, reproducibility, or cross-repository consumption, such as whether generated clients, canonical fixtures, release evidence, or deployment manifests are versioned.

The Repository Build Design owns the semantic categories and protected exceptions; the physical repository's `.gitignore` or equivalent owns exact pattern syntax. When the repository exists, prefer one repository-local verification command that uses `git check-ignore` or an equivalent deterministic mechanism and is included in aggregate verification. The Software Design validator checks that the policy and verification route exist; it does not inspect commits, staging state, or other user-managed Git state.

### Repository discovery handoff preflight

Run this preflight whenever a user asks to create or refresh a Stage 9 handoff for a repository, even when its record already says `discovery_status: complete`. It is a design/readiness check, not physical repository creation.

1. Resolve the selected Build Units to their first-party `REPO-xxx` records and read the repository design, member Build Units, applicable CONS/RC records, linked SEL/VA records, and mapped ticket records.
2. Confirm that the repository design states the implementation-critical construction contract: repository/workspace shape, package and module paths, public entrypoint/export boundaries, owned target outcomes and runtime-profile commands when applicable, required bootstrap/seed/migration and persistence/reset surfaces, required fixture/deployment/release surfaces, selected toolchain and commands, the three repository contract coverage lanes, the complete Version-Control And Generated-File Policy, and any architecture or pattern choice that affects boundaries, verification, or maintainability.
3. Automatically derive conventional files, scaffolding, ignore entries, and safe template exceptions implied by those choices. Do not turn file existence, local path, ordinary cache/output patterns, or private helper organization into user questions. Ask only material alternatives that would change architecture, public seams, verification, security, release behavior, reproducibility, or cross-package consistency; explain the recommendation and consequences.
4. For each missing material choice, create a normal `TICKET-NNNN` implementation-detail ticket under the existing ticket workflow, map it to every affected Build Unit, set `repositories` to every affected `REPO-xxx` Repository Build Design, and stop the readiness pass. Use the ordinary ticket interview batch rules. A resolved repository-specific must/must-not becomes or updates an `RC-xxx` rule; a reusable toolchain or implementation choice becomes or updates an `SEL-xxx`; a system behavior or correctness change routes back to Software Design.
5. Reconcile ticket status, repository discovery, contract coverage, version-control policy, and the canonical repository record after answers are written. `discovery_status: complete` means the implementation-critical repository contract is explicit, every applicable coverage lane is inherited/resolved/adapted/not-applicable with evidence, the must-track/must-ignore/generated/secret/verification boundary is concrete, and no material repository decision is silently left for the builder; it does not require enumerating every private helper file.

Do not create a current Stage 9 delivery-slice handoff, or claim `IMPLEMENTATION_DETAILS_READY`, while this preflight has created unresolved material repository tickets, while a coverage lane lacks an explicit disposition, or while resolved outcomes have not been reflected in the Repository Build Design, derived agent-guidance artifact, and reciprocal ticket/build-unit records.

### Delivery-slice realizability challenge

Run this mandatory semantic challenge after repository discovery and before Stage 9 promotes any selected slice. This is the Stage 8 exit gate for Delivery Readiness; it does not create a new numbered stage. Re-read the selected source closure from its canonical files. Do not infer correctness from `finished` tickets, `complete` discovery, structurally valid links, or an earlier handoff.

Before running probes, enumerate the complete bounded cohort: the selected slice, direct and transitive prerequisites consumed during implementation/build/selected-slice verification, and every known target-version consumer reached through existing interface and Build Unit bindings. Run every safe independent probe in that cohort even after another probe fails. A failed prerequisite blocks only probes that depend on it; record those separately and continue unrelated checks. Group all failures by canonical root cause and affected probes/slices. Do not write or promote a ready handoff after any failure. After repairs, rerun the same complete cohort once and require a zero-new-blocker result. This is a bounded diagnostic sweep, not a global blueprint audit and not an implementation pass.

Evaluate every selected unit and direct dependency against these eight core realizability axes, followed by the five compatibility axes in the handoff template:

1. **Source consistency:** compare Build Units, Repository Build Designs, CONS/RC records, SEL/VA records, and linked Software Design contracts for mutually incompatible instructions, schemas, states, formulas, or lifecycle claims. Exercise at least one negative or boundary scenario for each mechanism-critical interface.
2. **Required-input closure:** enumerate every deployment identity, address, hash, credential, generated artifact, fixture, external fact, configuration value, and immutable package or image named by the selected source closure. Continue through every producer's own prerequisites until each leaf is a selected-slice output, a verified existing input, a later-lifecycle output, or missing; do not stop at a cross-repository package name or a source-complete producer. Record the result under `Required Input Ledger` as one `INPUT-NNN` entry per value, or an explicit evidence-linked `None.` declaration when the slice truly consumes no inputs. Each entry names the consumer Build Unit and consumption stage, kind, producer Build Unit or external owner, producer repository and stage, availability, maturity, evidence, optional later-lifecycle gate, and immutable-artifact receipt fields. Use availability only from `selected-slice output`, `verified existing input`, `later-lifecycle output`, and `missing`; use maturity only from `source-only`, `built`, `published`, `accessible`, `verified`, and `not-applicable`. These states are not interchangeable: source implementation does not prove publication, publication does not prove authorized access, and access does not prove exact-version integrity or successful resolution. For a pre-existing immutable artifact consumed by implementation, build, or selected-slice verification, require the exact immutable identity, source revision, integrity, successful resolution check, and successful authorized-access check, each backed by current evidence from the producing repository or registry. Never record a credential value; record only the safe access-check result. Do not classify an input as missing solely because a consumer-specific lock, checksum, install, fetch, or access receipt cannot exist until an explicitly bound repository is scaffolded: when producer evidence establishes the exact artifact and the Repository Build Design fixes the ordinary acquisition, authentication, and verification route, record that receipt as workpack bootstrap evidence. Classify the input as missing only when the artifact or identity is unavailable, the acquisition route remains undecided, or a concrete access failure has no ordinary workpack remedy.
3. **Interaction closure:** enumerate every required logical-to-physical interaction, its shipped or selected-output binding, representation conformance, consumer path, failure meaning, and proof class. Apply the bounded positive/rejection/failure matrix only to high-risk interactions.
4. **Toolchain realizability:** verify every exact runtime, library, compiler, plugin, and package-manager selection against authoritative local metadata, a lockfile, or the package registry. Check existence, engine ranges, peer dependencies, and command compatibility. If compatibility cannot be verified, block readiness instead of assuming it.
5. **Responsibility projection:** enumerate the material responsibilities and public seams in each selected Build Unit's `Source Responsibility Mapping` and `Module Architecture`. Confirm that the allowed delivery slice preserves each one or names a canonical, valid exclusion. A summary label is not evidence of complete responsibility coverage.
6. **Verification adequacy:** map every behavior, compatibility, security, state-transition, artifact, and target-outcome claim to a VA or concrete command/procedure that can actually observe it in the claimed environment. A command name or planned harness is not adequate when it cannot exercise the relevant runtime, browser, service, failure mode, boundary input, or intended entrypoint.
7. **Execution-context readiness:** identify the physical target repository or explicit future-repository binding, required environment/services, user-supplied inputs, and setup assumptions. Keep Git state user-managed, but do not let downstream execution guess which repository or external prerequisites the handoff targets.
8. **Target-outcome closure:** for every declared target outcome and runtime-profile claim, trace the intended actor or consumer through the real selected entrypoint, assembly owner, configuration and bootstrap, required state and dependencies, and minimum observable result. The proof must fit the artifact: runnable application/service path, real CLI invocation, installed library consumer, representative pipeline execution, or isolated infrastructure provision/dry run. A test harness cannot satisfy a runnable-use claim unless it is itself the selected target. Fixed fixture identities, resources, balances, or provider fakes must remain inside an explicit test or demo composition and cannot silently supply a normal deployable entrypoint.

For each later-lifecycle output, add one handoff-local `LGATE-NNN` record under `Later-Lifecycle Gates`. Name the consumption stage (`Release`, `Deployment`, `Activation`, or `Operation`), canonical producer, exact gate condition, verification procedure, and the claim or action prohibited until satisfaction. Do not use a gate as a substitute for an input required by implementation/build/test, and do not map it to a deferred design ticket unless an actual material choice remains unanswered. A gate limits later lifecycle claims; it does not exclude a selected Build Unit responsibility that can already be implemented and verified. Paid-service subscription, production credentials, public deployment, and provider activation may remain later gates when the required non-production outcome has an approved behaviorally faithful substitute; the substitute still cannot prove the real provider or production profile.

Build the temporal prerequisite graph from every `INPUT-NNN` consumer-stage → producer-stage edge. For every participating Build Unit, also add the intrinsic lifecycle edges `Operation → Activation → Deployment → Release → Verification → Build → Implementation`. Reject the handoff when this graph contains a cycle, including a path where an implementation-stage input requires a release whose own prerequisites return to that unit's later deployment or release stage. A declared `selected-slice output` must be produced by a selected Build Unit; a declared `later-lifecycle output` cannot satisfy Implementation, Build, or Verification. Reconcile every cross-repository producer against its current delivery evidence rather than treating a physical source tree, finished ticket, or old handoff as an available artifact.

Record the bounded result in the handoff's `Delivery Slice Realizability Review`. Every axis must be `PASS` with a concrete conclusion and at least one canonical local link before `IMPLEMENTATION_DETAILS_READY` or `IMPLEMENTATION_DETAILS_PARTIAL` may be claimed. Use `BLOCKED` and route the gap to its canonical owner when any producer needed by the selected implementation/build/test slice, compatibility fact, responsibility, or proof route is missing or contradictory. A later-lifecycle output may coexist with `IMPLEMENTATION_DETAILS_READY` when the selected implementation can complete without it and its `LGATE-NNN` guard prevents premature release/deployment/activation/operation claims. The validator checks required-input record shape, declared lifecycle consistency, declared temporal cycles, immutable receipt completeness, and local evidence-link existence. It does not rerun external commands or prove that prose evidence is truthful; only the fresh Stage 9 challenge supplies that semantic evidence, so validator success must be reported as structural validity rather than semantic completeness.

For every new or refreshed handoff, also record a Physical Realizability Closure. Treat one `PSEAM-NNN` as a compatibility equivalence class: several inputs and interactions may share one entry when they use the same producer output, consumer rule, runtime profile, implementation situation, and correction fate. The initial finite coverage universe is exactly every selected `INPUT-NNN`, every selected `INT-NNN`, the declared target outcome, required commands, protected changed interfaces, mechanically known direct consumers, and directly affected implementation surfaces. An inventory item may be added only through a concrete import, manifest, lock, generator, generated output, fixture, test, verifier, command-call, or exact-identity dependency from an existing item. Freeze that inventory before repair and rerun it unchanged afterward.

Classify each seam as `new-output`, `existing-unchanged`, or `implemented-evolution`; classify its boundary as `protected-machine-interface`, `required-effectful-command`, `change-impact`, or `ordinary`. Compare the applicable dimensions—schema/version, identity/representation, transport/method, topology/ports, authority/caller, lifecycle/persistence, and command/toolchain behavior—and explicitly explain inapplicability instead of manufacturing checks. Existing prerequisites require current observation through their real public seams. A protected-machine-interface `implemented-evolution` requires a focused candidate representation to pass through the real existing consumer seam before readiness; source inspection or a planned future proof is insufficient. A genuinely `new-output` seam may plan final proof when every correcting and proof owner is in the writable selected slice. For every delta, enumerate and disposition source/imports; tests/fixtures/golden values; dependencies/manifests/lockfiles; generators/generated outputs; identity/freshness/receipt verifiers; and configuration/evidence. Inspect actual side effects for required commands that build, deploy, regenerate, migrate, or invoke another repository; ordinary lint and unit-test commands do not require deep command inspection. `COMPATIBLE`, `DELTA_OWNED`, and a canonical `EXCLUDED` result can support readiness; `BLOCKED` cannot. This is a bounded semantic receipt, not a demand to run the complete not-yet-implemented product or audit unknown future consumers.

For `SEL-xxx` and `VA-xxx` records, `technical_sources` names canonical `SR-xxx`, `FLOW-xxx`, or contract IDs in frontmatter. Do not encode a prose list and recover identifiers heuristically.

Build Design ends with one of:

- `BUILD_DESIGN_MAPPED`: the requested build-unit map is explicit and structurally valid, though units may remain blocked.
- `NOT_REQUIRED`: the selected scope already inherits a compatible build-unit and module shape. Do not create a Markdown overlay solely to restate it.
- `NEEDS_TECHNICAL_DECISION`, `NEEDS_PRODUCT_DECISION`, or `NEEDS_USER_APPROVAL`: the named boundary cannot be mapped without an unresolved upstream or material choice.

### Stage 9: Delivery Readiness

Use Delivery Readiness only when the user wants to hand selected build units or a cross-unit slice to downstream planning. Run the repository discovery handoff preflight and the delivery-slice realizability challenge before evaluating the handoff outcome. Every material ticket mapped to a `READY` selected unit must be `finished` or explicitly `out-of-scope`; `decided` is allowed only for a `PARTIAL` unit whose unresolved capability is canonically excluded from the declared slice. A `todo` or `deferred` ticket blocks readiness. Every selected first-party repository must have `discovery_status: complete` with an explicit implementation-critical construction contract, complete repository contract coverage, a concrete Version-Control And Generated-File Policy with a verification route, and a derived agent-guidance artifact; a mapped but blocked repository remains useful Stage 8 evidence, never a Stage 9 handoff route.

Delivery Readiness ends with exactly one of:

- `IMPLEMENTATION_DETAILS_READY`: every selected unit is implementable and verifiable for the declared delivery slice, every applicable core and compatibility axis passes, and the handoff identifies a credible verification route. Explicit later-lifecycle gates may remain when their outputs are not consumed by this slice.
- `IMPLEMENTATION_DETAILS_PARTIAL`: a narrower declared slice passes every applicable core and compatibility axis while every unresolved item is explicit and outside that slice.
- `NEEDS_TECHNICAL_DECISION`, `NEEDS_PRODUCT_DECISION`, or `NEEDS_USER_APPROVAL`.
- `NOT_REQUIRED`: existing repository evidence already supplies the needed realization and no Markdown overlay is necessary.

Never use `IMPLEMENTATION_DETAILS_PARTIAL` to plan around unresolved in-scope work. Also never use it merely because a fully specified value or artifact will be generated at a later release, deployment, activation, or operation stage; use `LGATE-NNN` while keeping the implementable unit `READY`.

Set readiness from whether a normal downstream workpack can implement and verify the declared slice, not from whether bootstrap has already run. Repository or folder scaffolding under an explicit future binding, exact dependency installation, package-manager authentication through an already-defined route, lockfile or checksum generation, and consumer install/fetch receipts are ordinary workpack bootstrap and do not block readiness. Use a non-ready outcome only for a concrete unresolved in-scope decision or prerequisite that cannot be satisfied during that workpack. `NEEDS_USER_APPROVAL` requires a specific user decision or action that must occur before planning or implementation can proceed; lack of authorization for an unrelated external mutation is not such a blocker. Later-lifecycle controls and explicitly out-of-scope tickets do not block readiness.

## Source Routing And Classification

Read only the Domains, System Responsibilities, flows, contracts, TD records, tickets, and repository files affected by the Build Design scope. Read the canonical behavior owners and approved requirement sources when the missing answer changes user behavior, operating outcome, or product scope.

Classify each detail before editing:

- **Software Design repair:** changes behavior, authority, lifecycle, system interface, invariant, or correctness. Route upstream.
- **Product decision:** changes user-observable behavior, permitted outcome, product scope, or operating policy. Use an existing `kind: product` ticket inside Software Design, obtain approval for material unresolved choices, and reconcile the approved answer into canonical responsibilities, flows, state, and contracts.
- **Material implementation selection:** determines a build-unit boundary, runtime, major library, persistence model, environment, command, security/cost constraint, or reusable verification route. Own the unresolved workflow in a `TICKET-NNNN` ticket and the approved/inherited reusable result in an `SEL-xxx` when justified.
- **Reversible local choice:** does not change a protected contract, build-unit boundary, environment, command, or Verification Obligation. Record it briefly in the owning build-unit file.

Before requesting approval for a material choice, explain the concrete gap, viable options, consequences, reversibility, protected Software Design truth, and recording plan. Do not ask the user to approve labels or filenames without the underlying model.

## Tickets, Selections, And Verification

Tickets own unresolved workflow and history. After Build Units exist, `build_units` records realization applicability while `owner` and `affects` retain logical Domain/System Responsibility ownership. When a ticket establishes or changes a durable technical rule, `constraint_refs` routes to its CONS record; `result_refs` remains limited to SEL/VA results. Do not move or duplicate ticket files into Build Unit or repository folders.

Use `SEL-xxx` only for a reusable material implementation selection. States remain `Proposed`, `Approved`, `Inherited`, and `Deferred Outside Selected Scope`. Use `VA-xxx` only for a reusable environment, fixture system, simulator, testnet, or harness—not for ordinary unit checks. SEL records preserve selected implementation direction, and VA records support evidence for named Software Design claims; neither one defines system behavior, authority, interfaces, lifecycle, or correctness claims.

Use `BUILD_UNIT:BU-xxx` as the affected-scope identifier in SEL and VA records. `technical_sources` identifies the logical responsibilities, flows, and contracts preserved by the result. Cross-cutting results list every affected Build Unit. Keep reciprocal ticket `result_refs`, SEL/VA `source_tickets`, Build Unit links, and handoff links synchronized.

A ticket may produce an SEL, a VA, both, a build-unit update, or a Software Design repair. Do not create result IDs for their own sake. An inherited SEL or existing VA may omit tickets only when it records concrete repository or environment evidence.

For greenfield work, mark commands and planned verification as `Planned — unverified until scaffold exists`. Never claim execution evidence before code or a harness exists.

## Build Entry Contract

Once a package contains its first Build Unit, make `build/README.md` the detailed human construction guide for the whole Build Design. A reader must be able to understand what every Repository and Build Unit is like without opening its ticket, Build Unit record, or Repository Build Design. Keep the root Software Design README as the package index and definitions entry point; do not create another summary file, generated view, Project README, or Repository/Build Unit summary issue.

Begin the build README's substantive content with `## Construction At A Glance`. Group every first-party Repository exactly once under a linked `### REPO-xxx — Name` heading and list every member Build Unit exactly once inside that Repository block. Put a Build Unit with no first-party repository under `### External Or Unassigned Build Units` with its explicit disposition. Preserve canonical Repository membership rather than inferring it from ticket labels or dependencies.

For each Repository, explain in one or more short paragraphs:

- what the repository is for and its workspace shape;
- why its Build Units belong together; and
- how those units relate through their material public artifacts or dependencies.

Give each Build Unit its own linked `#### BU-xxx — Name` block. Explain what it does and produces, why its build/test boundary is separate, where it lives or its external disposition, how it connects to the rest of the construction, and the authority or responsibility it deliberately does not own. Use as many short paragraphs as clarity requires; do not impose a one-sentence limit. The guide must be detailed enough to supply a usable construction mental model, without copying exact mappings, module trees, constraints, interfaces, commands, or verification obligations from the linked canonical record.

Keep the identifier-and-name form in reader-facing headings. ## Build Unit Detailed Code Shape

`### Detailed Code Shape` is a subsection of the human `## Build Unit Overview`; the exact `### Module Architecture` contract sits under `## Agent-First Canonical Reference`. The visual answers, at a glance: where material code belongs, which selected actions or capabilities the unit provides, which public seam a caller reaches, and which execution, state, component, or proof shape warrants attention. It is a synchronized reading layer, not a second implementation plan, ticket summary, or canonical owner of those facts.

Derive it from approved, selected, or inherited canonical records. A ticket may define the question or seed a proposed action surface, but a finished ticket is historical workflow evidence: preserve its resolved action/interface/state outcome in the relevant Build Unit, interface or contract, state model, `SEL-xxx`, or `VA-xxx` record first, then project it into Detailed Code Shape. Do not invent actions, signatures, component ownership, test guarantees, or file paths merely to complete the visual.

Use the fewest blocks necessary for the unit's material shape. Choose from:

- **Material scaffold:** for a new or materially reshaped code unit, show a shallow but materially complete planned tree. Include source roots, public entrypoints, cross-boundary interface/type/schema locations, persistence/authority/state owners, generated/release/evidence boundaries, and proof-owning test roots. Normally expand one or two levels; go deeper only where a material seam, owner, or proof boundary needs it.
- **Supported Actions:** when the unit has a selected action or capability surface, show every selected action. Group them by lifecycle, authority, or caller only when that helps scanning. Include material reads, recovery, expiry, and administrative actions rather than showing only happy-path writes.
- **Public seam:** show exported signatures, routes, events, types, commands, or interfaces when an action map alone does not explain how a caller crosses the boundary.
- **Critical shape:** show a compact call tree, pseudocode, state branch, or component tree only when it carries a material lifecycle, security, correctness, orchestration, or ownership concern.
- **Evidence shape:** show test roots, fixtures, and critical scenarios only when reusable evidence infrastructure or a non-obvious verification boundary is material.

For a UI Build Unit, prefer a behaviorally meaningful component tree: include page-level composition, state owners, meaningful hooks, and module boundaries; omit purely presentational leaves. For a small library, one export/type block may be enough. Omit routine private helpers, every individual test case, vendor directories, caches, build output, and ordinary configuration. The detailed Build Unit sections remain authoritative for exact paths, interfaces, constraints, commands, and Verification Obligations.

The Build Design validator requires the dual-audience shape and checks that a present `Detailed Code Shape` is in its required reading layer with non-placeholder visual content. It cannot prove semantic completeness; writers must reconcile the reading layer with its detailed canonical sources.

## Material Interaction Bindings

Stage 5 interfaces own logical cross-responsibility truth; Stage 8 Build Units own its physical realization. For every material cross-Build-Unit or external interaction required by a unit, add one row under `Material Interaction Bindings` with:

- route, export, event/topic, artifact path, command, generated-client entry, or manual handoff;

A consumer/verifier is not a producer; missing, ambiguous, duplicate, or malformed action-role rows block validation;
- canonical schema, type, wire format, or other representation source;
- public/internal/authenticated/authorized audience or named operator;
- the conformance procedure; and
- `Planned` or `Verified` state.

Do not list ordinary private helpers or framework callbacks. A unit with no material cross-unit or external interaction uses the `Material interaction bindings` field with `None.` and a concrete reason. Every Build Unit that produces or consumes a selected Stage 9 interaction must contain the binding before readiness can pass; do not rewrite unrelated units.

When one logical contract has multiple machine-consumable representations—such as an authoritative schema, HTTP adapter, generated client, event type, persisted projection, or fixture—name each material representation and one deterministic conformance route. This is conditional on the boundary having multiple representations; do not force a generated client, schema language, or code generator onto technologies that do not need one. `Not applicable` requires a concrete reason, such as a manual handoff with no machine representation.

## Claim-To-Evidence Classification

Classify proof by the strongest claim it actually exercises:

| Evidence class | What it can establish | What does not establish it by itself |
| --- | --- | --- |
| `existence` | The named route, export, artifact, command, or binding exists. | Existence does not prove shape, behavior, or usability. |
| `identity-freshness` | The checked producer/artifact/revision is the one the consumer will use and the evidence is current for the readiness run. | A historical report, branch name, or mutable version label. |
| `structural-conformance` | Material representations agree on required fields, types, status/error shapes, or encoding. | A schema file that was not compared with the exposed binding and consumer representation. |
| `behavioral` | Positive and applicable rejection/failure semantics execute as designed. | Compilation, mocks alone, or a route listing. |
| `consumer-fitness` | The actual consumer path can obtain and use the required producer result with the intended authority and failure meanings. | Producer-local tests, internal methods, fakes, or producer health checks alone. |

Evidence may support the same or a weaker class, never a stronger one by assertion. Mocks and fakes remain useful for consumer behavior, but they do not prove compatibility with a pre-existing producer unless the representation is deterministically conformance-checked and the consumer path is challenged against current producer evidence.

Exact producer revision or immutable identity is required only when drift could invalidate the fitness conclusion; record it in the Required Input Ledger or fitness evidence, not in a universal per-source hash manifest.

External consumers use **Consumer:** followed by `External` — a named actor/system and the exact canonical IFACE.ACT link. They are not Build Units. Require `**Proof owner:**` with one selected first-party `BUILD_UNIT:BU-xxx`, its canonical link and a relevant explicit action binding. The external `Consumer path` names the real actor's entrypoint and links both the canonical action and proof owner. Physical binding may link that owner. Proof ownership is verification responsibility only: it creates no consumer identity, publication authority, dependency exemption or writable scope. Keep true BU consumer/producer role checks unchanged. An external producer's publication authority must remain distinct from selected observation, acknowledgement or job production.

For an interaction whose real external output is needed only at a later lifecycle stage, `Availability: later-lifecycle output` requires all of these fields inside the same INT entry, without duplicate interactions or new registries:

- `Later-lifecycle gate`: one existing `LGATE-NNN` whose consumption stage equals the interaction's later `Required at` stage.
- `Lifecycle inputs`: existing `INPUT-NNN` identities with that same producer, gate and later consumption stage. Preserve their actual external authority in the canonical source; matching the token `External` alone cannot prove identity.
- `Current-profile inputs`: existing Implementation/Build/Verification INPUT identities for this interaction, or `None.` with a source-supported explanation in the profile field. Every required current input must be available or an owned selected output; an unavailable endpoint, credential, artifact or fixture needed now still blocks planning. Do not omit an early dependency to relabel it later.
- `Current-profile availability`: `verified existing interaction` or `selected-slice output`, governing the entry's current conformance and consumer challenge. Existing proof requires current identity/freshness, conformance and independent PASS; selected output may plan final proof only with an already writable selected proof owner and the existing physical-compatibility prerequisites satisfied.
- `Current-profile verification`: link the approved runtime/verification profile and explain the bounded consumer path, substitute or acquisition route, evidence/proof owner and authority limits. Separate local consumer evidence from independent-provider operating evidence; fixture success never certifies the real provider. Retain required evidence classes and high-risk cases.

A gated external `Producer` must name its independent authority and link the exact canonical action. These fields are inapplicable to ordinary current interactions; a `missing` disposition cannot be bypassed by attaching a gate. The current profile must independently pass its prerequisites and physical realizability review. Keep real activation evidence pending and mandatory, including any prohibition on early use, commitment or availability claims; a later gate does not authorize a dependency required by the selected scope. A `Planned` current test is not a provider receipt. Validators cross-check declared identities, stages, availability and scope; the bounded semantic review must still detect unjustified deferral, omitted dependencies, false receipts and authority substitution. Never infer semantic completeness from structural success.


Set interaction risk to `high` only when a failure could materially affect security, authority, funds, irreversible state, protocol correctness, data compatibility, or safe recovery. Only `high` interactions require a bounded verification matrix naming positive, rejection/denial, and failure/recovery cases. Ordinary interactions explicitly use `None.`. This keeps the gate proportional and prevents an unbounded test-matrix loop.

## Workflow And Validation

For an explicitly selected delivery, document-shape findings in Build Units or repository reading sections outside the selected units, transitive prerequisites, and required known-consumer coverage are non-blocking package-maintenance notices. Keep those findings visible without repairing unrelated records in this pass. Full Build Design/package validation remains strict. Identity, relationship, constraint, dependency, proof, and compatibility failures remain blockers; missing or ambiguous coverage cannot justify treating a relevant record as unrelated. This changes diagnostic disposition only, not interaction derivation or whole-system impact analysis.

1. Identify whether the request is Build Design, Delivery Readiness, or both. Confirm Stage 7 snapshot completion when available; otherwise apply the bounded current-state check above, because receipt absence alone does not block Build Design.
2. Inspect the selected Software Design truth, Technical Constraints, tickets, and permitted repository evidence.
3. Classify missing choices and route any upstream conflict.
4. For a human-facing scope, consume the Stage 7 specification and selected candidate, linking reviewed journeys before finalizing affected Build Units; for a non-UI scope, record the not-applicable disposition without creating the folder.
5. Define or update stable Build Units and their many-to-many source-responsibility and CONS mapping, first-party repository home, and code path.
6. Create/update a Repository Build Design for every first-party source repository, then run repository discovery with member-unit CONS coverage and any justified RCs.
7. Add `build_units` or an explicit empty-array disposition to every active ticket once Build Design exists.
8. Record module architecture only inside the unit it belongs to.
9. Create or update justified SEL/VA results and reciprocal links.
10. For Delivery Readiness, freeze the direct-dependency-bounded inventory, run every safe independent check, materialize the complete Required Input Ledger, Required Interaction Closure, Physical Realizability Closure, applicable Required Verification Obligation Closure, and the target-outcome/runtime-profile contract, execute safe registry/resolution/access checks, reconcile cross-repository evidence, reject temporal prerequisite cycles, challenge every pre-existing protected machine consumer with a focused candidate when its producer evolves, complete exact known-consumer and directly affected-surface coverage, inspect required effectful command behavior, trace the minimum acceptance outcome through the real entrypoint, and for human-facing slices reconcile prototype/specification consistency plus separate functional and UI/UX implementation-review routes. Group failures by canonical root cause and block every semantic contradiction, unavailable prerequisite, incomplete immutable receipt, missing interaction, unwritable required change, unassigned or unmapped VO, incompatible exact selection, responsibility or assembly-ownership gap, inadequate proof class, failed conformance, unresolved mapped current-scope ticket, repository discovery gap, or unresolved UI/UX blocker. After repairs, rerun the same frozen inventory once and require zero new blockers before readiness.
11. Record the eight core realizability axes, including `Interaction closure` and `Target-outcome closure`, plus the five compatibility axes and the applicable VO routing conclusion under `Verification adequacy`; reconcile the selected-unit handoff only after the required-input ledger, interaction closure, VO closure, outcome/profile closure, UI/UX delivery review when applicable, and realizability review pass for the allowed slice.
12. Generate and check the handoff's revision Snapshot ID after the selected canonical sources have been reconciled into its final content.
13. Create or refresh the compact `build/README.md` construction guide from the canonical Repository and Build Unit records.
14. When at least two build units exist, create or refresh the canonical Build Unit Dependency Map and direct links from the package README and `build/README.md`.
15. Run all applicable validators, plus UI/UX validation when the folder exists and Canvas layout validation when the dependency map exists, before reporting mapping validity or readiness.

The ticket validator checks ticket shape, logical ownership, Build Unit applicability, and TD parent synchronization. The Technical Constraint validator checks constraint shape and routing. The Build Design validator checks Build Unit records, repository/constraint routing, the compact construction guide, and reusable-result synchronization. The snapshot command writes and verifies one identifier for the normalized current Stage 9 handoff; it does not audit linked-source freshness. The Delivery Readiness validator first requires valid Build Design, then checks the snapshot, selected-unit routing and writable subset, required-input ledger shape, declared temporal-cycle absence, immutable receipt completeness, Required Interaction Closure structure, Build Unit binding references, evidence-class declarations, conformance/challenge status, proportional high-risk matrices, local evidence links, complete `PSEAM-NNN` coverage, implemented-evolution candidate proof, direct impact-category disposition, writable ownership, frozen-inventory termination, the eight-axis outcome-aware realizability receipt, and the five compatibility axes. A new or refreshed handoff lacking the required closure is not ready for planning or operability claims. The assurance coverage validator checks the current blueprint assignment universe and each affected implementation repository's manifest and binding coverage without running tests. It does not rerun registry, install, authorization, conformance, consumer-challenge, or evidence commands. The dependency-map validator checks that the Stage 8 graph exactly represents the canonical units and their reduced dependency structure. The layout validator checks geometry. None proves semantic completeness by itself; never create the receipt by mechanically marking its axes `PASS` merely to satisfy validation, and never describe validator success as proof of external availability.
