# Expert consultation

Use this workflow for natural requests such as “Prepare the accounting questions for my accountant” or “Process the answers in this brief.” No predefined profile, expertise registry, GitHub access, or new ownership field is required. Read [implementation-detail-tickets.md](implementation-detail-tickets.md) for canonical recording and approval rules.

## Prepare the selected questions

Infer the requested subject and recipient from the request and existing sources. Ask only when a material ambiguity prevents selecting a useful scope. Use existing tickets and their canonical requirements across Build Units and System Responsibilities; do not limit selection to one folder or treat Build Units as logical owners. Preserve initial inventory timing: this is a selected consultation, not an early or project-wide inventory pass.

Follow `depends_on` transitively, including prerequisites outside the initially selected set, and inspect relevant `blocked_by` facts and canonical write targets. Check that connected requirements agree and that prerequisite links exist. Report missing references, cycles, or contradictions within this closure; do not expand into a project-wide audit. A settled prerequisite contributes approved context, not another unanswered question. If the bounded inspection exposes a missing material prerequisite, propose or refine an ordinary ticket through the existing workflow rather than inventing a consultation-only dependency record.

Order unresolved questions by actual decision prerequisites, preserving the complete requested selection and topic hierarchy, including waiting questions. Within topics put prerequisites first; order whole topics when possible. When dependencies interleave topics, retain coherent sections and provide explicit cross-topic references plus a valid answering sequence in the introduction. A category-level cycle is not necessarily a ticket cycle; page order and grouping never create dependency edges. Deduplicate by canonical ticket identity, including shared tickets; explain each material effect on the selected responsibilities and Build Units in reader-friendly names. Existing primary ownership remains unchanged. A shared decision is not automatically a product-owner decision: determine whose knowledge or authority is needed from the actual question.

- If the same expert can answer a prerequisite, include it explicitly, even when it was outside the initial selection, and rerun analysis before export. Explain the concrete consequence for later choices.
- If someone else must settle an unresolved prerequisite, resolve or separate it explicitly. The dependent question cannot request a final answer yet. It may collect examples or provisional preferences, clearly identifying what remains open and whose decision is needed without inventing an owner field.
- For a conditional recommendation, name the assumed earlier choice and explain how another answer changes the available alternatives. Say when clarification or reformulation is required before answering. Do not hide a prerequisite in a recommendation or assume the recipient will infer it.
- Requests for easier or harder questions use `complexity` only among questions whose prerequisites permit discussion. Never reorder a dependent question ahead of its prerequisite to satisfy that preference.

### Prepare coherent remaining questions

Before export, compare the selected questions, alternatives, and recommendations with relevant approved answers and current canonical requirements. Separate what is already decided from what genuinely remains open. Ask for advice on the remaining choices without asking the recipient to decide the same matter again or presenting obsolete alternatives as valid choices. When expanding alternatives into subquestions, preserve their meaning, scope, configuration granularity, assumptions, and recommendation; an editorial expansion must not silently change the decision. Keep proposals explicitly provisional and never invent an approved answer.

Apply the active task's authorization. When canonical ticket repair is authorized, use [the existing repair workflow](checkpoint-workflow.md#upstream-repair-handling) and [ticket synchronization rules](implementation-detail-tickets.md#ticket-and-td-synchronization) to reconcile affected wording/options without reopening approved decisions. Document generation alone does not authorize ticket edits. Report a material canonical inconsistency to the requesting user, naming the affected part and the minimum repair needed. Continue preparing unaffected questions and keep the requested selection visible. For an affected part that can usefully collect provisional input, state precisely what advice is requested and why a final decision is not yet requested; if no useful advice can be collected, retain the selected question with the concrete preparation action needed. Do not stop the whole consultation, require extra approval for routine wording within the authorized task, or substitute a generic warning for question preparation.

### Scoped read-only analysis

Resolve the skill directory as the directory containing the active `SKILL.md`. Select tickets semantically from the request and relevant sources; the helper does not infer expertise from kinds or folders. Run from any working directory:

```sh
node <software-design-skill-directory>/scripts/report-ticket-answerability.mjs --root <software-design-package> --ticket TICKET-0001 --ticket TICKET-0002 --json
```

Omit `--json` for human-readable output. Use explicit `--all` instead of ticket selection only for a requested whole-inventory inspection. The command uses the current version-3 parser and normal ticket locations, without requiring unrelated classification or Build Design metadata. It does not invoke the whole-package validator or any provider.

The report retains selected identities, prerequisite order, approved context, internal prerequisites, direct facts, waiting causes with explanatory paths, deduplicated outside notices, graph relationships, and localized review findings. An ordinary question can be `answer-now`, `answer-after`, `waiting`, or `needs-review`; approved/deferred/excluded dispositions remain explicit. These are transient labels, never canonical status fields. Factual blockers are distinct by source ticket and text. Repeated propagation of the same blocker produces one notice with one deterministic explanatory path per affected question. Identical text on different tickets does not establish shared meaning. The writing agent may consolidate their presentation only after semantic confirmation, retaining every source reference; no canonical blocker ID or registry is introduced. Internal prerequisites and outside causes can coexist. Independent branches remain usable even when other selected questions have cycles or outside blockers. Never invent an order for cyclic nodes. Historical ancestry behind approved answers is review context rather than propagated waiting.

Exit 0 means analysis completed, including ordinary waiting and review findings; inspect those findings before preparing notices. Invocation, missing inventory directory, inventory without recognized `*-tickets.yaml` files, unreadable file, or parser/index failures exit 1 with an explicit diagnostic and no successful report. All ticket files must parse for a trustworthy identity index, but unrelated graph defects outside the selected closure do not block selection. No canonical files are written and no legacy values are repaired.

## Create the editable brief

DOCX is the default. Start from [expert-consultation.docx](../assets/templates/expert-consultation.docx), a neutral reusable presentation template. Its sample text is scaffolding to replace, not product requirements. Use available document tooling, such as python-docx; resolve runtime and rendering tools in the current environment, never embed machine-specific runtime paths in the skill. Read the template's paragraphs, styles, sections, headers, and embedded mapping before replacing content.

Preserve this presentation. Reusable instructions, template examples, and default labels are English; localize reader-facing text only to the requested recipient language.

- Opening: write a standalone working document by default. Use current approved context instead of “What changed since the previous consultation”, “new in this consultation”, prior agent recommendations, or removed dependency-link history. Include history only when explicitly requested or materially useful to the recipient; preserve substantive approved context and meaningful source attribution. Put routine change summaries in the completion message. Retain purpose, scope, preparation date, essential shared context, and short response instructions. Move topic-specific approved context beside the relevant questions; put additional reference context later when useful. Avoid repeating the same explanation in the opening, topic introduction, and ticket. Preserve decision-critical explanations without an arbitrary page limit.
- Contents: replace dense ticket inventories with numbered topics, descriptive titles, and working internal links. Include accurate printed page references where useful. Keep only a concise dependency summary and any necessary cross-topic answering sequence; local notices must make the opening blocker list unnecessary.
- Topics: each starts with a next-page section and a numbered Word Heading 1. Immediately below it, add a small secondary count line such as “1 ticket” or “2 tickets”. Count distinct canonical tickets actually included in that topic after selection is final, excluding prerequisite mentions and repeated continuation headings. Preserve prominent repeating topic headers on every page, including continuation pages, plus page numbering. Unlink section headers and keep default, first-page, and even-page variants consistent. Use generous margins, black Calibri headings, a 24 pt document title, 19 pt ticket headings, 13 pt bold subquestion headings, and 11 pt body text.
- Tickets: use Word Heading 2 in the exact form `TICKET-0117 — Descriptive ticket title`, prefixing the title with its canonical ID on the same heading line rather than a separate secondary ID line. Immediately below it, show “1 question”, “2 questions”, etc., derived from the included subquestions. Count each question once, excluding prerequisite mentions and repeated continuation headings. Keep the visible ID consistent with its one canonical bookmark and embedded mapping. Use numbered Word Heading 3 subquestions, restarting at 1 within each ticket. Preserve this reading order: canonical ID and descriptive title → question count → applicable notice → relevant approved context → concrete remaining question → example where useful → alternatives and consequences → recommendation with reasons → assumptions where needed → editable response space. A subquestion-specific notice follows that subquestion heading before its context and alternatives.
- Questions: supply understandable context, detailed alternatives and consequences, a recommendation with reasons and explicit assumptions when appropriate, and editable response space. Introduce options before referring to them only as “A”, “B”, or “C”; put option-specific examples beside the relevant option. When evidence is insufficient, explain what would support a recommendation instead of inventing one.
- Include respondent name and response date, and space for clarifications, exceptions, incorrect assumptions, missing requirements, and concerns unrelated to existing tickets. Preserve editable paragraphs rather than images or locked controls. Omit complexity by default.

### Preserve emphasis and explanatory depth

Use black Calibri throughout the reading hierarchy: 24 pt title, 20 pt topic headings, 19 pt ticket headings, 13 pt bold subquestion headings, and 11 pt body. Preserve the template's generous 0.8 inch side margins, 7 pt body paragraph spacing after, approximately 1.12 line spacing, and visible heading separation. Keep secondary counts visually subordinate. Do not shrink text to meet a page target.

Use the populated template's reusable styles rather than replacing whole paragraphs with unformatted text:

- `ConsultationOption` paragraphs contain a bold `ConsultationOptionTitle` run for the option letter and descriptive title, followed by regular-weight explanation and consequences. A bold letter alone is insufficient; do not bold the whole explanation.
- Apply `ConsultationNoticeLabel` to each availability label within its existing notice paragraph style. Keep its explanation regular weight and preserve internal links.
- Use the bold character styles `ConsultationContextLabel`, `ConsultationQuestionLabel`, `ConsultationExampleLabel`, `ConsultationRecommendationLabel`, `ConsultationAssumptionLabel`, `ConsultationAnswerLabel`, and `ConsultationCommentsLabel` for their supporting labels. `ConsultationSupport` provides ordinary paragraph spacing; the body after each label remains regular weight. These are presentation roles, not canonical fields or mandatory sections.

Within the existing topic/ticket/subquestion hierarchy and local notices, explain relevant approved context beside the question it informs, then the concrete remaining question, an example where useful, understandable alternatives and consequences, recommendation rationale, necessary assumptions, and editable answer/comment space. A descriptive subquestion heading can introduce the subject before its notice and context; avoid restating the same question unnecessarily. Omit inapplicable sections rather than adding boilerplate. Keep option-specific examples beside their option. Preserve enough explanation for the expert to understand the practical trade-offs and why a recommendation applies; distinguish proposals from approvals and conditional advice from final choices.

When updating an existing consultation, make targeted corrections while preserving its established presentation and useful explanations. Do not summarize the whole document, move substantive question context to an appendix, or merge supporting sections merely to reduce page count or fit a question on one page. Remove obsolete consultation history without deleting useful current context. A presentation reference supplies visual conventions, not current business truth; never restore superseded alternatives or dependency wording from it.

For font portability, inspect effective formatting across document defaults, paragraph styles, their base styles, applied character styles, linked heading character styles, and direct run formatting. Keep explicit Calibri and black settings free of competing font-theme and theme-color attributes in the used style chain; align linked heading character styles with their paragraph counterparts. Preserve supported style identifiers and unrelated theme definitions. Check populated runs, not only declared heading styles. Verify the actual renderer's result and report viewer-specific uncertainty; one renderer does not establish compatibility with Word or another viewer.

### Local availability notices

Interpret the actual cause before choosing reader-facing wording. Internal analysis labels such as `answer-now`, `answer-after`, `waiting`, and `needs-review` are evidence for review, not an unconditional one-to-one mapping to notices. In particular, a deferred prerequisite awaiting a known confirmation is waiting for that confirmation; it is not an unspecified dependency problem. Question preparation and dependency answerability are separate concerns. These presentation distinctions add no canonical statuses, mapping fields, or workflow registries.

Use the template's restrained paragraph styles with plain English defaults: `ReadyToAnswer` (“Ready to answer”), `AnswerAfter` (“Prerequisite”), `WaitingFor` (“Pending confirmation”), and the existing `DependencyReview` style (“Question needs revision”). The retained style identifier supports existing documents; it does not dictate the displayed label. Adapt the wording to the real missing answer, fact, or preparation issue rather than copying a label mechanically.

- A resolved prerequisite normally supplies approved context, including when outside the document. Use “Already decided” and “What remains to decide” where useful, followed by the concrete remaining question, valid options, recommendation, and answer space. Preserve meaningful source attribution without forcing an external-location warning onto approved context.
- For an unresolved ticket prerequisite, use “Prerequisite” as the default label. Identify the answer needed, name each affected question by number and descriptive subject, and explain how that answer changes its available choices. State what conditional preference, example, or other provisional input remains useful. Avoid unclear referents such as “both questions”, “after resolving it”, or “answer later”. Answering the consultation does not automatically change a canonical ticket's status.
- For an internal prerequisite, name its canonical ID and descriptive title once in the notice, retain a hyperlink to that ticket or the relevant subquestion, and state its verified location naturally: “You will find this ticket on page 3 of this consultation.” Do not add “Click its code” instructions or a redundant location suffix in the label. For an external ticket, explicitly say it is not included in this consultation. Do not add external GitHub links.
- For a pending external fact or action, identify the missing confirmation directly without inventing a ticket or owner. Trace known waiting through intermediate or deferred prerequisites to the actual pending confirmation, retaining each distinct cause. Use “Pending confirmation” rather than presenting a fact as an unanswered ticket. Being outside does not imply a different owner.
- When an approved answer makes the CURRENT QUESTION's wording or options incomplete or contradictory, prepare a coherent remaining question under the authorization rules above. If material revision remains necessary, label that part “Question needs revision”, explain the specific defect and useful next action, and collect only explicitly identified provisional advice. Mention the resolved source as supporting context, not as an outstanding blocker. Do not offer obsolete alternatives as current choices or repeat assurances such as “do not answer the resolved ticket again”.

Location remains independent of readiness. Place each explanation at its applicable scope: a prerequisite shared by all questions in a ticket gets one notice beneath the ticket heading and question count; a prerequisite affecting only one question gets its notice beside that question. An additional question-specific dependency explains only that additional condition. Do not duplicate a shared notice beneath every question. Consolidate only genuinely shared explanations, preserving all distinct prerequisites and external causes and their separate effects. Do not infer independent subquestion readiness from a ticket-level report alone. Do not make unaffected questions or options appear blocked. Keep context and response areas editable; recommendations never count as approved prerequisites.

The template demonstrates one capacity-unit prerequisite shared by booking-confirmation and cancellation questions. Its single ticket-level notice names the separate effect on each question; local notices in another ticket demonstrate pending confirmation and a current question needing revision. Approved decisions remain nearby context, not outstanding blockers or questions to ask again.

Availability paragraphs are the narrow exception to restrictions on flow markers and decorative blocks: restrained paragraph shading, borders, or color may distinguish them from ordinary bold prose. Keep explicit text understandable in grayscale. Do not add decorative topic blocks, colored dependency diagrams, or additional hierarchy levels.

### Navigation and pagination

Use actual Word heading styles and outline levels. Give topic and optional subquestion navigation anchors a separate namespace, such as `nav_topic_1` and `nav_capacity_unit`; never duplicate a canonical ticket bookmark for navigation or continuation headings. Contents links must target those headings, and prerequisite links must target the named ticket or subquestion. Use a populated linked contents list with verified page references or a refreshed Word TOC, never an unpopulated field placeholder. Recheck page references after the last layout change; an update-on-open flag alone is not verification.

Keep short questions, option sets, recommendations, and response spaces together when they reasonably fit. Use keep-with-next selectively within short units, keep-lines and widow/orphan controls, and sensible breaks between long-ticket subquestions. Do not force every ticket onto one page, shrink body text, or chain a long ticket into a large blank area. Avoid orphaned headings and unexplained options at the top of pages. Where a long question must continue, retain descriptive ticket/question identity beside the continued unit, without adding another canonical bookmark. A repeating topic header alone may not identify the question sufficiently. Do not repeat a full notice merely because a page breaks or another subquestion begins. Add a brief prerequisite reminder only when a long continuation cannot be understood independently without it; retain the original full explanation at its applicable scope.

### Minimal embedded mapping

Keep mapping inside the DOCX, not a separate ledger. Use a Word bookmark around each ticket heading named `ticket_TICKET_0001` for canonical `TICKET-0001`; subquestion numbers are local to that heading, not new canonical IDs. When repeating a heading for orientation, retain only one canonical bookmark. The template includes an example bookmark and a `customXml/item1.xml` embedded mapping. Replace both when preparing a real brief.

The mapping stores the canonical package's relative path, preparation date, each included ticket's ID and title, and relevant source references (ticket files and canonical requirements, including external prerequisites). This mapping identifies the questions and their sources; it is not a source baseline or a second workflow registry: do not store statuses, readiness, owners, or response-processing state in it. Existing tickets remain the only tracking records. Derived overview/notices add no mapping fields. Returned documents without an overview remain processable through the same bookmarks, XML mapping, and current-source comparison rules. Preserve the custom XML ZIP part, its content-type declaration, and relationship when saving; confirm the bookmark-to-ticket mapping and source references survive the final save. If document tooling strips them, restore and verify them before delivery.

In the existing final review, check the selected questions for content consistency:

- Recalculate numerical examples and their dependent values when assumptions change; keep quantities, units, rates, and totals consistent.
- Ensure recommendations correspond to the available answer choices and response instructions. A single-choice question must not recommend selecting multiple options; revise the choices or instructions to express the intended decision consistently.
- Support material legal or tax claims used to justify options with authoritative sources and the applicable jurisdiction, period, and conditions. If the rule or its applicability is uncertain, ask the expert to establish it instead of presenting it as settled.
- Keep proposed answers and conditional recommendations distinct from approved project requirements, including in question context and examples.

Render the final DOCX and inspect every page for coherent question/option grouping, distinct local notices, heading hierarchy, persistent topic headers, editable answer space, clipping, and unnecessary blank areas. Verify ticket/question counts against the final selection and check rendered contents and prerequisite page references against their actual destinations. Verify link destinations, not only the presence of XML anchors. Adjust pagination and rerender after layout changes. For reusable template changes, also render a temporary longer sample with topic continuation pages, several subquestions, a shared ticket-level prerequisite, and additional question-specific conditions; keep that stress content out of the reusable template. Compare representative pages with any supplied presentation reference for hierarchy, label and option emphasis, adjacent context, explanatory depth, and answer-space placement. Check all pages of the temporary sample as well as the template, and keep temporary rendering artifacts outside the repository. XML contract tests must check semantic formatting roles and effective font/color inheritance in populated content, alongside mapping, navigation, and counts; do not substitute global bold-run counts or frozen sample wording for those checks. Structural tests supplement visual inspection rather than replacing it. Verify the embedded mapping, content type, relationship, and unique ticket bookmarks after the final save. If rendering is unavailable, report that limitation instead of claiming visual verification.

## Reconcile returned answers

Read the completed brief, including freeform concerns. Resolve bookmarks to existing tickets and confirm the original package and question meaning against the embedded mapping. If markers were lost or headings changed, use the embedded mapping and canonical titles to propose a mapping; clarify ambiguities rather than guessing or duplicating tickets.

Always compare returned answers with current canonical requirements and the directly affected prerequisites and dependents, including those outside the exported selection. Do not assume an unchanged title or the exported context means the design is current. Use history only when needed to resolve ambiguity. If the mapping or source references are missing or ambiguous, make the uncertainty explicit and clarify it rather than guessing; inspect the relevant current sources before proposing reconciliation. Do not create a replacement baseline or tracking mechanism.

For each mapped answer, explain whether it agrees with current requirements, is provisional on an unanswered prerequisite, contradicts current truth, or reveals a new material requirement. Check consequences for the existing canonical owners and write targets, dependent recommendations, and existing Build Unit mappings. Surface unanswered prerequisites and contradictions before proposing a final resolution. A changed foundation can invalidate a later answer even when the expert answered both questions.

Use existing approval distinctions, write-target rules, completion checks, and ticket/TD closure workflow. Expert input is evidence and advice; it does not automatically approve a design change, mark a ticket decided, or complete it. Record an approved resolution through the existing workflow and set finished only after canonical reconciliation and required checks. Create or refine ordinary tickets only for warranted material findings, including concerns that have no existing ticket; do not create one per comment or clarification.

Importing answers does not authorize prototype edits. Record affected later prototype work in the existing UI/UX specification's `Change Synchronization` pending-work entries and preserve manual synchronization under [ui-ux-design.md](ui-ux-design.md). Keep readiness claims limited to the selected scope and stop once this bounded reconciliation is complete.
