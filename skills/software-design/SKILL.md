# Software Design

Create and maintain an implementation-grade `software-design/` package. Preserve approved product and technical truth in an agent-first logical system model, keep the root README as the package index with generic Blueprint Terms only, and keep build construction, reusable build records, decisions, and workflow artifacts in their exact owners for later delivery planning.

## Design Workspace

For new repository-scoped work, use `<repository-root>/design/` as the design workspace: `software-brief.md` and `software-design/` are siblings there. If no repository root exists, use `<workspace-root>/design/`.

Resolve paths in this order: explicit user paths; exactly one existing package/brief pair under `design/` or the repository root; otherwise the new `design/` defaults. If multiple candidates are plausible, stop and ask which pair is canonical. Never move an existing package or create a duplicate merely to adopt the default. Create `design/software-design/` only after Stage 0 approval. For ticket projection from the repository root, use `design/software-design` as `ticketRoot`.

Read [references/package-layout.md](references/package-layout.md) before creating, repairing, or structurally validating a package. `system-model/` owns Domains, System Responsibilities, behavior data, flows, and atomic contracts; `build/` owns Build Units, repositories, records, and workflow; the root README owns navigation and generic Blueprint Terms only. Derive cross-unit realization coverage from reciprocal System Responsibility and Build Unit fields; do not create a standalone topology summary or a parallel generated summary surface. Never modify a consumer blueprint merely because this skill or its templates changed.

This skill owns approved software product behavior, technical architecture, UI/UX, and delivery readiness. Intake, implementation execution, deployment, and code-level implementation planning remain separate. Broader product framing and research are outside this workflow.

## Invocation And Source Boundary

For a new staged package, use a reviewed `software-brief.md` from `$software-design-intake` or an equivalent human-reviewed software brief. If none exists, ask for one or recommend `$software-design-intake`; do not silently turn rough source material into a technical blueprint.

When continuing or reviewing an existing `software-design/` package, follow the user's source restriction. If the user says to use that package only, do not read, validate against, or discuss the software brief, product package, blueprint, or another upstream artifact unless the user later authorizes it.

For ordinary staged creation, read the complete brief before the first checkpoint. Treat its technical summary, mechanism trace and registers, proposed logical boundaries, main flows, constraints, assumptions, review points, open design-around items, deferred scope, and final Software Design goal as source truth when present. When an upstream brief calls those logical boundaries “components,” interpret them as System Responsibilities; do not preserve the overloaded package term merely because the source used it.

Open design-around items are constraints, not automatic blockers. Stop only the affected work when:

- a required source is missing or contradictory;
- the System Responsibility map or authority boundary is genuinely ambiguous;
- proceeding would collapse distinct states, objects, credentials, artifacts, or external domains;
- proceeding would invent a mechanism-critical transition or automatic handoff;
- proceeding would choose an unresolved product or technical decision without approval; or
- an approved earlier artifact and the active source disagree materially.

Record unresolved product behavior in existing `kind: product` tickets. Obtain user approval for material choices and conflicts with approved requirements. Once approved, record behavior in the owning System Responsibilities, flows, state, and contracts; tickets retain question and resolution context, not duplicate specifications. Preserve external authority and source attribution when applicable. Design around safe local gates, continue unaffected Domains, and withhold only the affected readiness claim. Do not create another decision register or new statuses.

## Core Design Audits

### Application Surface

When the source names a product surface, account, participant, operator, approval workflow, or approval agreement, verify that every human-facing responsibility belongs to an in-scope System Responsibility, an external system, or explicit deferred scope. Cover identity and roles, authentication and recovery, drafting and consent, API/orchestration, durable records, notifications, status projection, the canonical parameter dictionary, and the separation between product records and enforcement authority.

Do not let a protocol-only responsibility map silently stand in for the product application. Do not treat an actor as a System Responsibility or a Build Unit.

For a human-facing surface, apply [UI/UX Design](references/ui-ux-design.md) proportionately. At Stage 0 establish the intended users, main tasks, product-versus-demo boundary, and basic experience expectations, reusing approved upstream UI/UX ownership by reference. During Stages 1–7 identify material interface questions and their canonical owners. Before exploration, establish only the prerequisites needed to frame a meaningful bounded comparison: intended task, affected owners, known authority and safety constraints, and the hypotheses being tested. Explicit prototype hypotheses may help answer material questions about behavior, state, routes, recovery, or architecture; those questions need not all be settled first. Preserve approved answers in the existing canonical owners and resolve material contradictions before claiming reconciliation. Expose internal transitions, identifiers, implementation terms, or diagnostics by default only when they help the intended audience make an informed decision.

### Target Outcome And Runtime Profiles

For every code-bearing target, establish an artifact-appropriate acceptance outcome before using broad completion language. An application or service with a human or operator surface normally needs at least one approved non-production profile in which the intended actor can start or reach the real entrypoint and complete the minimum target journey; a CLI needs an invocable command and representative result; a library or SDK needs a real consumer installation and public-API use; a pipeline needs representative input-to-output execution; and infrastructure needs a reproducible isolated provision or dry run. An explicitly design-only, specification-only, or later-activation scope may choose a narrower outcome, but make that exclusion visible rather than assuming it.

Classify every named environment, network, platform, device, or operating mode by the exact claim required for the target version: build compatibility, verification only, runnable use, deployment, or activated operation. A profile may carry several claims, but a name such as `local`, `test`, `staging`, or `production` proves none of them by itself. For each required runnable profile, identify the actor or consumer, entrypoint, minimum observable outcome, dependencies, bootstrap or seed path, persistence/resume/reset semantics, external prerequisites or substitutes, and acceptance evidence.

Paid, credentialed, or externally provisioned services may remain later deployment or activation gates when an explicitly approved non-production substitute preserves the required local behavior and authority boundary. A substitute does not prove real-provider compatibility. Keep fixed identities, resources, balances, and provider fakes inside an explicit test or demo composition; a normal deployable entrypoint must obtain them from approved runtime sources unless the product is intentionally fixed to that identity.

Do not require a dedicated demo Build Unit universally. Create or select a Build Unit for operational composition only when startup, provisioning, profile configuration, seeded state, persistence/reset, or cross-artifact assembly forms an independently buildable and verifiable artifact. Otherwise keep the outcome inside the existing owning unit. Distinguish `Software Design complete`, `Build Design complete`, `selected implementation slices complete`, `target outcome operable`, `deployable`, `activated`, and `production ready`; never collapse them into `finished` without naming the achieved level.

### Mechanism Preservation

When a mechanism trace or register exists, use it as a consistency contract. Before each affected checkpoint, identify and preserve:

- ordered transitions and terminal outcomes;
- distinct stateful objects;
- credentials, tokens, secrets, signatures, capabilities, and what each proves or enables;
- external-domain fact ownership;
- manual, automatic, evidence-bearing, and unresolved cross-system handoffs; and
- invariants and `must not imply` constraints.

Do not expose raw registers as default output sections. Express their truth through the package artifact that owns the architecture, interface, flow, state, or correctness rule.

## Staged Blueprint Workflow

Read [references/staged-design-workflow.md](references/staged-design-workflow.md) before proposing or writing a staged package. It owns the output shape, stage-specific artifact rules, templates, and final handoff.

Use this stage order unless the user explicitly changes it:

0. Pre-write package confirmation, including bounded UI/UX framing when a human-facing surface is in scope.
1. System-model architecture foundation and canonical decision setup.
2. System Domain records, one Domain at a time.
3. System Responsibility records, derived from the approved Domain.
4. Canonical lifecycle data and flow records.
5. Atomic interface, state, invariant, security, and scope contracts; when invariant or security records exist, use one Architecture-owned stable `assurance_id`.
6. Justified optional state-machine visuals.
7. Software Design completion, whole-package ticket inventory, and applicable UI prototype prerequisites, exploration, reconciliation, and completion.
8. Optional Build Design, consuming the reconciled Stage 7 UI/UX specification and selected candidate before affected Build Units are finalized, Verification Obligation assignment, and Runtime Architecture after diagram readiness.
9. Optional Delivery Readiness, selected-obligation closure, separate functional and implemented UI/UX review routes, and Delivery Planning handoff.

Stage numbers are writing order; `SR-xxx` identifiers are stable references, never implementation order. Later stages use approved earlier files and re-check the original mechanism source where permitted.

Before any staged write or material upstream repair, read [references/checkpoint-workflow.md](references/checkpoint-workflow.md). Every stage starts with an interpretation checkpoint and explicit approval. An approved Domain, System Responsibility, flow, contract family, or named section remains one active pass: resolve related sub-decisions conversationally and write the coherent records without requesting approval for each small edit. Require another checkpoint only for a material decision that remains unresolved or a behavior, authority, scope, boundary, or source-truth change outside the existing authorization. An explicit, unambiguous change request authorizes its affected upstream repair and reconciliation; resume the authorized pass afterward without another approval prompt.

For human-facing Stage 7 work, the UI/UX specification, bounded prototype exploration, journey-level reconciliation, and reviewed coverage form one authorized stage pass. Earlier bounded sketches are allowed when useful. Selecting a visual direction does not approve changed behavior; label exploratory hypotheses and resolve material contradictions before claiming reconciled design. An explicit prototype-change request authorizes the affected updates without another sync command or approval. After the initial reviewed prototype, batch later prototype work manually in the specification while updating canonical requirements normally. See [UI/UX Design](references/ui-ux-design.md).

Do not ask for blind approval. Explain the proposed model, material consequences, what remains unchanged, affected correctness obligations, classification, route, and expected recording plan before asking to write it.

## Technical Decisions

Read [references/technical-decisions.md](references/technical-decisions.md) before creating, splitting, changing, deferring, resolving, or backfilling a Technical Decision.

Canonical `TD-xxx` records in `build/workflow/technical-decisions.yaml` own one consequential coherent technical subject whose specific questions belong together. Each specific question remains one ordinary `TICKET-NNNN`; Software Design creates no separate question layer. Every canonical ticket declares `parent_decision` as one `TD-xxx` or explicit `null`. A standalone ticket is first-class and must not be forced under a TD merely for visual grouping. The `system-model/` architecture, Domains, System Responsibilities, behavior, and atomic contracts own stable system truth; TDs preserve the decision context and explain how their tickets fit after settled facts move to those durable owners.

Use only the established TD states: `Open`, `Partially Resolved`, `Deferred For Later Design`, `Blocked`, and `Resolved`. Derive the child set mechanically from ticket `parent_decision` values; do not maintain a second question registry.

A Blocked TD requires a concrete `blocker`. A defined deferred TD requires concrete `defer_reason` and `resume_when`, and every unfinished child must be `out-of-scope`. Vague future ideas and unrelated excluded work remain standalone tickets or Scope Boundaries. Run the Decision Closure Audit whenever an approved update finishes the last child, intentionally excludes a defined decision, changes a ticket's parent, or materially changes a scope boundary.

Detect TD candidates throughout design and run a final decision-cluster audit before the sequential ticket interview. For an existing blueprint, audit and propose groupings read-only before materializing them. Do not generate Markdown decision dashboards or a separate decision Canvas; GitHub `Decision Areas` is the human reading surface when projection is enabled.

## Implementation-Detail Tickets

Read [references/implementation-detail-tickets.md](references/implementation-detail-tickets.md) before creating or changing ticket YAML. Tickets own workflow state, the concise question, dependencies, resolution summary, write targets, and—after Build Design exists—affected Build Units. Canonical behavior remains in the architecture, Domain, System Responsibility, flow, atomic contract, Technical Constraint, implementation selection, Build Unit record, or TD record that owns it.

When a resolved ticket establishes or changes a durable technical `must` or `must not`, also read [references/technical-constraints.md](references/technical-constraints.md), create or update the canonical `CONS-xxx` record, and synchronize the ticket's `constraint_refs`. An unanswered ticket has no CONS result.

For answer recording and later presentation of affected unanswered tickets, follow [Ticket And TD Synchronization](references/implementation-detail-tickets.md#ticket-and-td-synchronization), including affected parent context and question wording.

### Batch Ticket Question Sets

When continuing a build unit or backlog, work through tickets one at a time; for the active ticket, present all its known material questions together. Give every question its own concise status line in this exact shape:

```text
TICKET-0042 · Q4/6 · Retry policy and failure evidence
```

The line names the ticket ID, question number, planned total questions, and a short label. A batch is not a compressed checklist: each question must retain the full one-question style—enough context to understand the decision, the actual choice, a clear recommendation and why, material consequences or alternatives where useful, and supporting sources when research was used. Never shorten a question merely because several questions are shown together. Do not manufacture extra questions for formatting or reversible local discretion.

The user may answer any subset directly (for example, `Q1 yes; Q2 explain; Q3 yes`). Record resolved answers, then discuss only the questions the user asks about; do not repeat or compress the whole batch in response. If the user explicitly asks to proceed one question at a time, follow that preference for the ticket instead.

The total is a plan, not a false guarantee. If a genuinely material new decision is discovered, state the replan explicitly before continuing, for example `TICKET-0042 · replanned Q4/6 → Q4/7`, then use the new total. Never change the denominator silently. When all planned questions are resolved, say `✓ TICKET-0042 complete · 6/6 questions resolved`; when starting the next ticket, say `▶ TICKET-0043 · Q1/5 · Artifact publication binding`.

Use this convention only while the live ticket-question interview is in progress. Do not use it in ordinary design discussion, clarifications outside that interview, commentary progress updates, validation results, GitHub synchronization messages, or unrelated work.

Do not require special syntax. Requests such as “find all remaining tickets,” “look for missing implementation tickets,” “complete the backlog,” or “check whether the backlog is complete” activate prospective inventory and require [references/ticket-inventory-mode.md](references/ticket-inventory-mode.md). A request to show or list the current backlog is a read-only status review. A request to backfill prior technical decisions into tickets activates decision-history backfill.

Prospective inventory, decision-history backfill, and status review are distinct. Do not create a ticket for an explanation, a derivable fact, formatting, implementation order, or reversible local discretion. Complete the initial discovery and challenge for the requested scope. After changes, review outstanding findings and directly affected dependencies, preserving completed coverage where relevant requirements have not changed. Repeat the full selected-scope review only when concrete evidence shows systemic omissions or unreliable coverage. Stop when material findings are reconciled and relevant checks pass; if missing information or an unresolved decision prevents progress, report partial completion and the exact blocker instead of repeating unchanged checks. Treat that result as bounded evidence, never as a claim that later decisions or implementation learning cannot expose new tickets.

Use exactly `todo`, `deferred`, `decided`, `finished`, and `out-of-scope`. `deferred` means a current-scope answer is temporarily postponed and still blocks readiness for that target version. `out-of-scope` means the capability is explicitly excluded from the target version and does not block it. Keep later delivery of an already decided design separate through `target_version`. A ticket becomes `finished` only after every canonical target contains the resolution and relevant validation passes.

After ticket creation, status or parent changes, TD creation or state changes, file moves, or write-target changes, run:

```sh
node <software-design-skill-directory>/scripts/validate-implementation-detail-tickets.mjs --root <software-design-package>
```

Resolve `<software-design-skill-directory>` to the directory containing the active `SKILL.md`; do not assume the skill scripts live in the consumer repository. The validator proves structural and synchronization consistency, not semantic backlog completeness.

### Repository Contract Coverage

For every greenfield or materially reorganized first-party repository, verify three separate contract lanes before declaring its Build Design or Delivery Readiness complete: `repository-module-conventions`, `code-construction-public-api`, and `maintainability-agent-guidance`. Read the maintainability baseline, inspect existing `AGENTS.md` and equivalent rules, and classify each lane as inherited, resolved by a repository-scoped ticket, adapted with an explicit exception, or not applicable with a recorded reason. If a material lane is not already covered, create a normal `TICKET-NNNN` ticket, map it to every affected `REPO-xxx` and `BU-xxx`, interview the user with a recommendation and alternatives, and stop readiness until its outcome is reflected in the Repository Build Design. Do not treat a generic coding preference, an assumed framework convention, or a brief recommendation as coverage.

Treat the repository's version-control and generated-file policy as a required sub-contract of `repository-module-conventions`. A complete Repository Build Design must state what must be tracked, what must be ignored, how generated outputs are classified, how secrets and safe templates are separated, and which repository-local procedure verifies the boundary. Derive conventional stack-specific ignore entries without interviewing the user; create or reopen a repository-scoped ticket only when a material choice remains, such as whether generated clients, reviewed release evidence, fixtures, or deployment manifests are versioned. Do not let an implementation or delivery agent invent that choice privately.

For a missing `maintainability-agent-guidance` lane, never present `maintainability-agent-guidance-baseline` as an opaque answer or ask the user only whether to inherit that identifier. Read [the baseline](references/maintainability-and-agent-guidance-baseline.md) and render one concrete decision packet in the repository-scoped ticket. The packet must state the recommended REPO-specific defaults, alternatives, and consequences for each of these six areas: simplicity and abstraction; duplication and refactoring; naming and rationale comments; agent change boundaries; stop/escalate conditions; and verification plus final-diff review. Distinguish inherited defaults from repository-specific adaptations and invite the user to accept or modify each numbered rule. A single cohesive lane ticket may contain the six numbered sub-decisions, but its `question`, `recommendation`, `options`, and live interview must expose the actual rules; the baseline identifier alone is never sufficient. When the recommendation is accepted, write the expanded rules into the ticket resolution and `build/repositories/repo-xxx-<slug>/agent-guidance.md`. The sibling repository `README.md` records the lane disposition and links the guidance; it does not duplicate the full rules.

## GitHub Ticket Projection

For GitHub ticket projection, run only the workflow in [references/ticket-projection.md](references/ticket-projection.md). YAML and canonical Software Design prose remain durable truth; GitHub Issues and the Project are collaboration views.

The [Project Presentation Contract](references/ticket-projection.md#project-presentation-contract) is the single maintained definition of views, fields, filters and visible order. Follow its current table rather than historical layouts. The Software and Product & Operations boards use the derived Board status field to separate ready todo tickets from Waiting tickets without changing canonical statuses. Use `project-view-audit` for initial setup, view changes or troubleshooting. Configure or repair views through `sync --views-only` for the settings GitHub's API can update, then saved changes in the signed-in GitHub interface for the rest, then a re-audit and browser verification of UI-only checks. The API connection order is not authoritative for tab position. Keep current and legacy projection identities stable; resolve identity collisions before creating anything. Installing the skill does not migrate consumer Projects.

The `Out-of-Scope` view is intentionally readable without a projection-only wrapper layer. A deferred TD receives both `Technical Decision` and `Out-of-Scope`, so the TD issue is the single top-level group and its body explains why the subject matters and how all child tickets fit. Its out-of-scope child tickets remain real, searchable canonical issues and remain in `All Tickets`, but they do not receive `Out-of-Scope`, so they do not repeat as top-level rows. A standalone out-of-scope ticket with `parent_decision: null` receives `Out-of-Scope` directly and keeps the normal human-first ticket body. Do not create standalone summary wrappers or duplicate TD summaries.

Use `reconcile` for read-only drift inspection and `sync` only when provider writes are authorized. The projection command holds a workspace-exclusive lock for `sync`; if it reports an existing lock, stop rather than launching another write. The local agent interprets comments; the mechanical adapter never makes a design decision. Run `pending-comments` and pass its clean-ticket-root preflight before interpreting GitHub discussion or editing canonical files. Do not bypass a dirty-root failure or treat comments as accepted decisions.

Route GitHub requests before running commands. A layout-only request uses `project-view-audit` for inspection or that view-repair procedure for configuration, without projecting every ticket; routine `sync` never starts view repair. Canonical ticket, TD, label, membership, or Project-field drift uses `sync` or read-only `reconcile`; a request containing both kinds uses both bounded workflows. The synchronizer must plan from one validated provider snapshot, keep shared setup sequential, run at most three distinct ticket or TD plans concurrently, preserve sequential ordering within each identity, consolidate managed ticket-label changes into one edit, and report progress, elapsed time, and exact partial completion without changing the final JSON result.

## Build Design And Delivery Readiness

At the Stage 8 → Stage 9 boundary, turn the stable Build Unit/repository dependency graph into one concise `build/workflow/handoffs/README.md` sequence index before creating the first slice handoff. Keep every delivery slice in one table with a unique repository-prefixed slug, explicit direct technical dependencies in `Requires`, and strictly sequential `Order group` values. Finish every slice in order group `N` before starting any slice in group `N+1`; only slices inside the same group may proceed in parallel. Treat the group as actual execution order, never dependency depth. Preserve completed group history, but recompute every unfinished group whenever a handoff is created or refreshed, readiness or blocker state changes, or dependency/scope evidence changes. Schedule runnable independent slices before blocked work they do not depend on; keep each blocked slice in the table at the earliest future position that does not stall such work. Use `Blocked — <exact reason>` for a slice with its own unresolved blocker and `Waiting` only for an otherwise unblocked slice held by earlier groups; `Blocked` takes precedence when both conditions apply. Default to one slice per repository and split a repository only when a proper Build Unit subset is independently buildable and verifiable, can become ready earlier, and every omitted member has a named later slice. Treat a delivery-slice slug as stable across later repository updates: when a post-implementation change remains inside an existing slice's repository and Build Unit coverage, refresh that slice's handoff and stable workpack paths instead of creating another slice. Prior implementation, a new package version, a new downstream consumer, or completed-group history does not justify a new slug or handoff. Keep the existing completed sequence row as history, do not add a repeat row for the delta, and express any unexecuted current requirement through the refreshed handoff/workpack/report lineage plus the exact blocker on a dependent future slice. Only implementation, build, and selected-slice verification prerequisites order handoffs; later release, deployment, activation, and operation outputs remain lifecycle gates. Reconcile and validate the README in the same pass as every handoff create or refresh. Treat it as mutable workflow navigation, never as a handoff receipt or snapshot owner.

Implementation-detail ticket YAML belongs to the `build/workflow/tickets/` lane and may exist after an affected System Responsibility's high-level design is approved. Ticket workflow does not create or activate optional Stage 8 `build/units/`, `build/repositories/`, or reusable records that are not yet justified.

Stage 7 completes the main Software Design through four mandatory ticket subpasses: ticket/TD parent synchronization and decision-cluster audit, independent standalone-ticket discovery, handoff and reverse challenge, and zero-delta completion against the approved snapshot. Parent synchronization is a prerequisite, never evidence that prospective discovery is complete. Run the inventory-lead report from [references/ticket-inventory-mode.md](references/ticket-inventory-mode.md), apply the counterfactual System Responsibility review there, and challenge every material `IFACE-xxx.ACT-NNN` from the consumer side: initial acquisition or observation, read-before-write when applicable, refresh/restart/recovery, empty/not-found versus forbidden versus stale/unavailable meaning, acknowledgement, and failure ownership. Also run the target-outcome and runtime-profile census: every required acceptance outcome needs an entrypoint, composition/bootstrap owner, profile claim, state/reset behavior, external-prerequisite disposition, and proof route. Give only applicable challenges a normal ledger disposition; do not manufacture tickets for an inapplicable operation kind. Return `TICKET_INVENTORY_PARTIAL` rather than declaring a current Stage 7 inventory complete when the independent pass or its coverage receipt is missing. For a shared producer consumed by several independently delivered first-party Build Units or profiles, also close the finite target-version public surface before that producer becomes executable: enumerate the known target-version actions, representations, compatibility rules, and consumer profiles, and finish only tickets capable of changing that surface. Unrelated tickets and unknown future consumers do not block it. Snapshot completion does not promise permanent backlog closure: later approved answers, source changes, or implementation learning may create or reopen tickets and require a delta review of only the affected boundaries. Preserve the initial whole-scope discovery and challenge; verify repairs through the impact-based follow-up in that reference, including connected producer/consumer effects. Repeat the full review only for a concrete systemic omission or unreliable responsibility/handoff coverage. That later discovery does not retroactively invalidate Stage 7. Applicable Stage 7 UI completion also requires the agreed prototype coverage and relevant reconciliation; material journey contradictions remain blockers. The package may otherwise be complete while `todo`, `deferred`, or `out-of-scope` tickets remain; report that distinction instead of treating unresolved implementation details as an unfinished blueprint.

**Stage 8 — Build Design** creates the concrete construction model under `build/`: stable `BU-xxx` records in `units/`, repository folders under `repositories/`, and justified `SEL-xxx` and `VA-xxx` records. Decided `CONS-xxx` records may already exist and are mapped into the construction model. Make `build/README.md` the detailed construction guide, while exact Build Unit and Repository records remain canonical. Map System Responsibilities many-to-many to Build Units through exactly reciprocal `realized_by` and `source_responsibilities` fields. Bind every material cross-Build-Unit or external `IFACE-xxx.ACT-NNN` in each affected Build Unit's `Material Interaction Bindings`; allow a concrete `None.` disposition only for genuinely interaction-free units. For every required target outcome and runtime profile, assign its composition, entrypoint, bootstrap, state-lifecycle, and acceptance-proof ownership to existing Build Units or create a new Build Unit only when that composition is itself independently buildable and testable. A repository-root command or test harness without an owning Build Unit does not close a claimed runnable outcome.

Stage 8 consumes the Stage 7 specification and selected candidate from [UI/UX Design](references/ui-ux-design.md); it does not defer required exploration to Build Design. Use its selective routes into the portable design module. Every Build Unit records explicit `applicable` or `not-applicable` UI/UX applicability plus a concrete disposition; applicable units link reviewed specification journeys and the actual selected candidate in `UI/UX Realization`. Libraries, background services, and other non-UI targets require no prototype. Stages 8 and 9 remain optional for design-only scopes.

When structured `INV-xxx.VO-NNN` or `SEC-xxx.VO-NNN` records exist, apply [Assurance Traceability](references/assurance-traceability.md): assign every VO to at least one Build Unit, require one planned tracked `assurance/coverage.yaml` per affected first-party implementation repository, and keep the generated blueprint-wide report outside both the canonical package and implementation repositories.

**Stage 9 — Delivery Readiness** creates one current handoff per selected delivery slice. A `deferred` ticket blocks the target version; an `out-of-scope` ticket does not block a handoff that explicitly excludes it. A `READY` Build Unit requires every mapped ticket to be `finished` or explicitly `out-of-scope`; `decided` means reconciliation is still incomplete and therefore is not executable. Before any readiness claim, run the repository-discovery preflight, reconcile ticket mappings and unresolved Build Unit statements in both directions, and derive the required interaction set from selected Build Unit responsibilities plus every relevant interface's producer and consumer mappings. When a ticket materially changes interface behavior or representation, map every Build Unit already bound through that interface's producer and consumer responsibilities; do not guess unbound or hypothetical consumers. A write target alone is not proof of material change because a ticket may perform structural, formatting, or provenance reconciliation. An interface without complete `Material Interactions` blocks the affected handoff. Materialize the full direct and transitive prerequisite closure as a complete Required Input Ledger of `INPUT-NNN` records and a complete Required Interaction Closure with one `INT-NNN` record per required logical-to-physical interaction. Every new or refreshed handoff also declares the artifact-appropriate target outcome, exact runtime-profile claims, selected Build Units, and the writable subset; proves target-outcome closure through the real selected entrypoint; and includes a finite Physical Realizability Closure that covers every input, interaction, and the target outcome. A verification harness cannot satisfy a runnable-use claim unless the harness is itself the selected product. When selected Build Units have structured VO assignments, also materialize Required Verification Obligation Closure; every selected assignment needs a concrete downstream manifest or external-evidence route, while planned evidence remains distinct from execution evidence.

For a selected human-facing slice under either `IMPLEMENTATION_DETAILS_READY` or `IMPLEMENTATION_DETAILS_PARTIAL`, also verify consistency among the reviewed prototype, canonical product and Software Design requirements, affected Build Units, and the handoff. Partial delivery cannot bypass requirements applicable to its selected UI scope. Route functional acceptance and implemented UI/UX review separately: both need explicit owners and evidence plans, and neither may be inferred from the other. Implementation review exercises meaningful outcomes, cancellation, and recovery and inspects typography, spacing, hierarchy, density, and responsive readability against the specification and selected candidate. The selected reviewed candidate is the implementation target; only details the specification explicitly permits may differ, and unillustrated material choices route to their design owner. Prototype approval is not implementation evidence or user testing; implemented UI/UX review is not actual user testing. Do not claim UI implementation readiness when the applicable prototype walkthrough has unresolved usability blockers, rendered prototype inspection has not occurred, or the implementation-review route is missing. If rendering is blocked, report the limitation and do not describe source inspection or structural validation as visual verification.

Distinguish source-only, built, published, accessible, and verified inputs, and preserve the claim-to-evidence limits in [the Stage 8/9 reference](references/build-design-and-delivery-readiness.md). In particular, consumer fitness must reach the shipped seam; selected-output producers use candidate representations before implementation and completed built proof afterward; only `high`-risk interactions require the three-case matrix; temporal cycles remain invalid; and later lifecycle outputs remain `LGATE-NNN` gates.

Every handoff uses the single Physical Realizability Closure and compatibility preflight structure. Freeze the initial inventory to the selected slice, its direct and transitive implementation/build/verification prerequisites, protected changed interfaces, mechanically known direct consumers, required workpack commands, and directly affected implementation surfaces. Add an item only when an existing inventory item has a concrete import, manifest, lock, generator, generated-output, fixture, test, verifier, command-call, or exact-identity dependency to it; never expand through speculation or an indirect product relationship. Run every safe independent check, group failures by canonical root cause, repair only the consolidated bounded findings, and rerun the same frozen inventory once. A new item on that rerun is a readiness-process defect that must name the previously unavailable direct dependency; it does not silently start another expanding audit.

Classify every `PSEAM-NNN` as `new-output`, `existing-unchanged`, or `implemented-evolution`. Compare observed producer output with observed consumer acceptance across the applicable dimensions that can invalidate the selected outcome: schema/version, identity/representation, transport/method, topology/ports, authority/caller, lifecycle/persistence, and command/toolchain behavior. Group facts with one compatibility fate into one equivalence class. Existing prerequisites require actual public-seam observations. A protected machine-consumable `implemented-evolution` with an existing producer and consumer requires a focused candidate representation through the real consumer seam before readiness; `PLANNED` is insufficient, while a genuinely `new-output` seam may schedule its final proof when every change and proof owner is writable in the selected slice. For each delta, close the directly affected source, test/fixture, dependency/manifest/lock, generator/generated-output, verifier/exact-identity, and configuration/evidence categories and inspect the effects of every required cross-repository, build, deploy, regenerate, or migration command against protected boundaries. Preserve the compatibility classifications and choose their least-coupled canonical evolution shape from settled facts; ask the user only when a real decision remains. A new or refreshed handoff without the complete closure is not ready for planning or an expanded completion claim.

After a canonical change, use the same reference's affected-slice audit to classify only explicitly mapped current slices, refresh only those affected, and defer a dependent workpack refresh until its required producer receipt exists. Report the audit transiently; do not create a second manifest, per-file hash system, or permanent change-impact artifact.

Set Stage 9 readiness from whether a normal downstream workpack can implement and verify the declared slice, not from whether bootstrap has already run. Repository or folder scaffolding under an explicit future binding, exact dependency installation, package-manager authentication through an already-defined route, lockfile or checksum generation, and consumer install/fetch receipts are ordinary workpack bootstrap and do not block readiness. Use a non-ready outcome only for a concrete unresolved in-scope decision or prerequisite that cannot be satisfied during that workpack. `NEEDS_USER_APPROVAL` requires a specific user decision or action that must occur before planning or implementation can proceed; lack of authorization for an unrelated external mutation is not such a blocker. Later-lifecycle controls and explicitly out-of-scope tickets do not block readiness.

Keep the existing identifier-and-name headings in reader-facing Build Design records. In human reading-layer prose and visual labels, use Repository and Build Unit names rather than bare `REPO-xxx` or `BU-xxx` identifiers. When a first cross-record mention in one reading layer needs traceability, write the name followed by its identifier in parentheses, for example `Public API (BU-002)`; use the name alone thereafter. This does not change frontmatter, filenames, agent-first references, dependency maps, tickets, handoffs, or GitHub projection.

For every first-party repository, Stage 8/9 must also complete the repository contract coverage audit defined in [references/build-design-and-delivery-readiness.md](references/build-design-and-delivery-readiness.md). A greenfield or materially reorganized repository is not contract-complete until its repository/module, code-construction/public-API, and maintainability/agent-guidance lanes are inherited, resolved by mapped tickets, or explicitly recorded as not applicable. After those lanes resolve, derive repository-scoped agent guidance from the baseline, canonical Build Design, and ticket outcomes; never treat `AGENTS.md` as a replacement for those sources.

Tickets own unresolved implementation workflow and history. Build Unit records own independently buildable artifacts, code locations, `source_responsibilities` mappings, physical `IFACE-xxx.ACT-NNN` bindings, internal module architecture, and unit-level commands. Every Build Unit leads with `## Build Unit Overview`, including a source-derived `### Detailed Code Shape`, before `## Agent-First Canonical Reference` and its exact construction sections. Repository Build Designs use the parallel `## Repository Overview`, optional `### Material Workspace Tree`, and `## Agent-First Canonical Reference` shape. A skill or template update never authorizes broad edits to an established consumer package. Before refreshing records, name the exact Build Units and Repository Build Designs in scope and make only the minimum source-backed correction. Never use a template as a diff target, normalize adjacent prose or links, or make cosmetic bulk edits. If canonical sources cannot support a concrete visual, make no record edit and report the missing truth. During Stage 8, justified `SEL-xxx` selections and `VA-xxx` capabilities own compact reusable outcomes for Delivery Planning. Keep ticket, Build Unit, selection, verification, and handoff links synchronized; do not require an SEL or VA merely to mark an answered ticket `decided`. Build Design may select local construction choices only when they preserve approved system behavior, authority, lifecycle, interfaces, and correctness claims. Route changes to those system contracts back through Software Design. Do not write a workpack or implementation plan in this package. Offer Delivery Planning only when the requested scope has a valid Delivery Readiness outcome, and never start it automatically.

Technical Constraints live under `build/records/constraints/` and own decided technical rules that Build Design must preserve. Implementation Selections and Verification Capabilities live beside them under `build/records/selections/` and `build/records/verification/`; they form one supporting-record family without sharing semantics. A Stage 8 Build Unit maps every applicable `CONS-xxx`. When several units share a source repository, create `build/repositories/repo-xxx-<slug>/README.md` as the canonical Repository Build Design and place its derived guidance at `agent-guidance.md` in the same folder after the guidance contract resolves. The repository design owns repository/workspace construction and any repository-only `RC-xxx` rules while compiling the member units' CONS IDs into an explicit applicable-constraint route. Do not make a builder search all Software Design prose or duplicate full guidance rules in both repository files. Before Stage 9, run `scripts/sync-technical-constraint-sources.mjs` and then `scripts/validate-technical-constraints.mjs`; the sync step deterministically adds missing links to every named canonical System Responsibility under each CONS's `## Scope And Sources`. A Stage 9 handoff must route the selected unit's Repository Build Design and exact CONS IDs as well as its SEL, VA, ticket, and dependency links.

After creating or refreshing a Stage 9 handoff under `build/workflow/handoffs/`, run `scripts/delivery-snapshot.mjs --root <software-design-package> --handoff <handoff-path> --write --check`. This writes one `sha256:` revision ID from the normalized handoff while excluding its own Snapshot ID line. It does not hash linked files. Put the exact dependency and artifact receipt values inside the handoff before snapshotting so the existing digest binds them without a separate receipt manifest or per-source hash list. Before writing the ID, reconcile the selected canonical sources and update the handoff wherever they change the delivery slice. Unrelated source changes that leave the handoff unchanged do not invalidate it.

Whenever a known workpack or implementation report exists for the slice, perform a post-implementation lineage audit before interpreting a changed handoff. If a genuine historical association cannot be established, use only the explicitly authorized [legacy-lineage recovery](references/legacy-lineage-recovery.md) route. Otherwise first require the existing workpack snapshot and report `Implemented snapshot` to match, then classify the complete change from the handoff, canonical sources, and physical repository:

- `No implementation impact` means only handoff or blueprint documentation, release evidence, publication, tagging, registry or repository permissions, exact-version resolution, authorized installation, or evidence-only records changed, with no implementation-owned tracked file change and no canonical requirement for one. Source, package manifests and lockfiles, build/runtime/release configuration, workflows, tests, fixtures, and verification scripts are implementation-owned. When the refreshed handoff receives a new Snapshot ID, copy that exact ID into the stable workpack, run the current workpack validator, and then set the existing implementation report's `Implemented snapshot` to the same ID. Do not create or execute a no-op workpack, create a separate reconciliation artifact, or leave the three IDs mismatched.
- `Implementation delta` means any implementation-owned tracked file changed, or the canonical design now requires such a change. Package repository metadata and release-workflow/configuration changes are implementation deltas. A mixed implementation-and-release change is always an implementation delta.

For an implementation delta, regenerate the affected handoff Snapshot ID, require a bounded workpack at that exact ID, and keep the prior `Implemented snapshot` plus any producer or downstream readiness claim unchanged until execution evidence names that workpack snapshot. Never synchronize the report to an implementation-impacting handoff before successful execution. Do not create a separate release snapshot, reconciliation artifact, change-impact record, or per-file hash list.
